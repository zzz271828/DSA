§ 1.2 Complexity Analysis

The time complexity of an algorithm is the amount of time it takes to run as a function of the input size. Rather than measuring actual wall-clock time (which depends on hardware), we count the number of basic operations performed. A basic operation is a single, constant-time step: an arithmetic operation, a comparison, an array access, etc.

The complexity of recursive algorithms is naturally expressed using recurrence relations: equations that express T(n) — the cost for input of size n — in terms of the cost for smaller inputs, together with base cases.

Definition — Recurrence Relation
A recurrence relation is an equation that recursively defines a sequence of values, with one or more base cases given. For example:

T(n) = T(n/2) + a  if n > 1,   T(1) = b

Solving Recurrence Relations

There are three standard techniques for solving recurrences:

  1. Substitution (unrolling / telescoping) — expand the recurrence step by step, identify the pattern, then substitute the base case.
  2. Verification by induction — guess the closed form, then prove it by induction.
  3. Master Theorem — a powerful formula for divide-and-conquer recurrences of the form T(n) = aT(n/b) + f(n).

Method 1 – Unrolling (Substitution)

The strategy is to repeatedly expand the recurrence to find the pattern, then reduce the general case to the base case. The example below analyses power1(x, n), which computes xn via repeated multiplication:

Algorithm: power1(x, n) — linear recursion T(n) = O(n) 
function power1(x, n):
    if n = 0 then return 1
    else if n = 1 then return x
    else return x * power1(x, n - 1)

Step-by-step solution:

  • Base case: T(1) = b
  • General recurrence: T(n) = T(n−1) + c
  • Expand: T(n) = T(n−2) + 2c = T(n−3) + 3c = ... = T(n−k) + k·c
  • Set k = n−1 to reach the base case: T(n) = T(1) + (n−1)·c = b + (n−1)·c
  • Simplify: T(n) = c·n + (b − c) = O(n)

Method 2 – Verification by Induction

To verify the solution T(n) = c·n + b − c for power1:

  • Base case: T(1) = c·1 + b − c = b ✓
  • Inductive step: Assume T(n−1) = c·(n−1) + b − c. Then T(n) = T(n−1) + c = c·(n−1) + b − c + c = c·n + b − c ✓

Example – Logarithmic Recurrence

The function power3(x, n) computes xn by squaring, reducing the input size by half at each step:

Algorithm: power3(x, n) — repeated squaring T(n) = O(log n) 
function power3(x, n):
    if n = 0 then return 1
    else if n = 1 then return x
    y = power3(x * x, floor(n/2))
    if n is even then return y
    else return x * y

Step-by-step solution:

  • Base case: T(1) = b
  • General recurrence: T(n) = T(n/2) + c
  • Expand: T(n) = T(n/4) + 2c = T(n/8) + 3c = ... = T(n/2k) + k·c
  • Set k = log2(n) to reach base case: T(n) = b + c·log2(n)
  • Result: T(n) = O(log n)

Time Complexity of Binary Search

Binary search is a clean example of a T(n) = T(n/2) + c recurrence. At each step, the search space is halved. Starting from n, after x iterations the search space is n/2x = 1, giving x = log2(n) iterations.

Algorithm: binary_search(array[1..n], key) Time: O(log n) | Aux Space: O(1) 
function binary_search(array[1..n], key):
    lo = 1
    hi = n + 1
    while lo < hi - 1:
        mid = floor((lo + hi) / 2)
        if key >= array[mid]:
            lo = mid
        else:
            hi = mid
    if array[lo] == key:
        return lo
    else:
        return null
Theorem — Time Complexity of Binary Search
The recurrence T(n) = T(n/2) + a, T(1) = b has solution T(n) = a·log2(n) + b.

Proof (by induction):
  • Base case: T(1) = a·log2(1) + b = a·0 + b = b ✓
  • Inductive step: Assume T(n/2) = a·log2(n/2) + b. Then T(n) = T(n/2) + a = a·log2(n/2) + b + a = a·(log2(n) − 1) + b + a = a·log2(n) + b ✓
Therefore, binary search has time complexity O(log n).

Key Insight — Master Theorem (Divide and Conquer)
For recurrences of the form T(n) = a·T(n/b) + f(n), the solution is determined by the relative growth of f(n) vs. nlogba:
  • If f(n) = O(nlogba − ε) for some ε > 0, then T(n) = Θ(nlogba)
  • If f(n) = Θ(nlogba), then T(n) = Θ(nlogba · log n)
  • If f(n) = Ω(nlogba + ε) for some ε > 0, then T(n) = Θ(f(n))
Example: Merge sort has a=2, b=2, f(n)=cn. Since nlog22 = n1 = n = f(n), we are in case 2, giving T(n) = Θ(n log n).

§ 1.3 Asymptotic Notation

Following the framework advanced by Turing Award winner Donald Knuth, when analysing the complexity of algorithms we concern ourselves only with the order of magnitude of the running time for large values of n. We express complexities using asymptotic notation, which ignores constant factors and lower-order terms.

Big-O Notation (Upper Bound)

Definition — Big-O
We say f(n) = O(g(n)) as n → ∞ if there exist constants c > 0 and n0 such that:

    f(n) ≤ c · g(n)   for all n ≥ n0

Informally: f grows no faster than g (up to a constant). Big-O gives an upper bound on the growth rate of a function. Note that bounds can be overestimates: it is correct to say both 2n + 1 = O(n) and 2n + 1 = O(n³).

Big-Omega Notation (Lower Bound)

Definition — Big-Ω (Omega)
We say f(n) = Ω(g(n)) as n → ∞ if there exist constants c > 0 and n0 such that:

    f(n) ≥ c · g(n)   for all n ≥ n0

Informally: f grows at least as fast as g. Big-Ω gives a lower bound on growth. Note: f(n) = Ω(g(n)) is equivalent to saying g(n) = O(f(n)). Bounds can be underestimates: n5 = Ω(n2) is valid.

Big-Theta Notation (Tight Bound)

Definition — Big-Θ (Theta)
We say f(n) = Θ(g(n)) as n → ∞ if and only if:

    f(n) = O(g(n))   AND   f(n) = Ω(g(n))

Equivalently: there exist constants c1, c2 > 0 and n0 such that c1·g(n) ≤ f(n) ≤ c2·g(n) for all n ≥ n0.

Big-Θ gives a tight bound — neither overestimate nor underestimate. For example: n² + 3n + 5 = Θ(n²), but n² + 3n + 5 ≠ Θ(n³) and n² + 3n + 5 ≠ Θ(n).

Little-o and Little-omega

Definition — Little-o and Little-ω
Little-o: f(n) = o(g(n)) means f grows strictly slower than g. Formally, for every constant c > 0, there exists n0 such that f(n) < c·g(n) for all n ≥ n0. Equivalently, limn→∞ f(n)/g(n) = 0.

Little-ω: f(n) = ω(g(n)) means f grows strictly faster than g. Formally, for every constant c > 0, there exists n0 such that f(n) > c·g(n) for all n ≥ n0. Equivalently, limn→∞ f(n)/g(n) = ∞.

The key difference: Big-O allows f = cg (equal up to constant), little-o does not.

Rules for Simplifying Asymptotic Expressions

  • Drop constants: O(3n) = O(n), O(100) = O(1)
  • Drop lower-order terms: O(n² + n + 1) = O(n²)
  • Multiplicative constants: O(c·f(n)) = O(f(n)) for any constant c > 0
  • Log base doesn't matter: O(log2 n) = O(log10 n) = O(log n) (since logs differ by a constant factor)
  • Polynomial dominates log: O(n·log n) = o(n²)
  • Exponential dominates polynomial: O(nk) = o(2ⁿ) for any constant k
  • Sum rule: O(f(n)) + O(g(n)) = O(max(f(n), g(n)))
  • Product rule: O(f(n)) · O(g(n)) = O(f(n) · g(n))

How to Prove Complexity Bounds

To prove f(n) = O(g(n)), find explicit constants c and n0 and verify the inequality directly.

Example — Proving a Big-O Bound
Claim: 2n² + 3n + 1 = O(n²)

For n ≥ 1:   2n² + 3n + 1 ≤ 2n² + 3n² + n² = 6n²
So choose c = 6 and n0 = 1. We have shown 2n² + 3n + 1 ≤ 6·n² for all n ≥ 1, hence 2n² + 3n + 1 = O(n²).

§ 1.4 Measures of Complexity

Best, Worst, and Average Case

For a given input size n, different inputs may cause the algorithm to take very different amounts of time. Let TA(I) denote the running time of algorithm A on input I, and let I(n) denote the set of all valid inputs of size n.

Definition — Best, Worst, and Average Case
Best-case complexity: tbest(n) = minI ∈ I(n) TA(I)
The fewest possible operations over any valid input of size n.

Worst-case complexity: tworst(n) = maxI ∈ I(n) TA(I)
The most operations the algorithm could execute on any valid input of size n.

Average-case complexity: tavg(n) = EI ∈ I(n)[TA(I)]
The expected number of operations averaged over all valid inputs of size n (assuming uniform distribution). Much harder to compute in general.
Common Misconception
Do not confuse "best case" with "small inputs" or "empty input". Best case refers to the most favourable input of a given size n. For example, the best case for searching is when the target is the first element checked — regardless of how large the array is.
Convention in This Unit
In FIT2004, unless otherwise specified, "complexity" means worst-case time complexity. We are primarily concerned with worst-case analysis because it gives a guarantee on performance for all inputs.

Time Complexity vs Space Complexity

Definition — Space Complexity vs Auxiliary Space Complexity
Space complexity: The total amount of memory used by an algorithm as a function of the input size. This includes the space for the input itself.

Auxiliary space complexity: The amount of memory used by the algorithm excluding the space for the input. This measures the "extra" memory needed.

Note: Many textbooks and online resources do not distinguish between the two, using "space complexity" when they mean "auxiliary space complexity". This unit uses both terms precisely.
Definition — In-Place Algorithm
An algorithm is called in-place if it has O(1) auxiliary space complexity — it only requires a constant amount of extra memory in addition to the input.

Some authors use a slightly different definition: an algorithm is in-place if it does not copy the input into any additional data structures, but modifies the input directly to produce the output (never storing more than O(1) elements of the input outside the input).

Examples: Selection sort and insertion sort are in-place. Merge sort is not in-place (the merge step requires O(n) auxiliary space). Binary search is in-place (O(1) auxiliary space).

Space Complexity Example — Binary Search

  • Space complexity: O(n) — the input array of size n must be stored.
  • Auxiliary space complexity: O(1) — only a few variables (lo, hi, mid) are needed.
  • Binary search is therefore an in-place algorithm.

Space Complexity Example — power1(x, n)

  • Space complexity: O(n) — each recursive call occupies stack space, and the recursion depth is n.
  • The iterative version power2(x, n) uses O(1) auxiliary space and is in-place.
  • This illustrates that recursive solutions often have higher space complexity than their iterative counterparts due to the call stack.

Output-Sensitive Complexity

Definition — Output-Sensitive Complexity
Output-sensitive complexity is the time complexity expressed as a function of both the input size and the output size. This is relevant when the output size itself can vary significantly.

Example: Given a sorted array of n unique numbers and two values x and y, find all numbers between x and y. The algorithm runs binary search to find the start (O(log n)), then scans until it exits the range. If there are w numbers in the range, the output-sensitive complexity is O(w + log n). In the worst case, w = n, giving O(n). But for sparse queries, the cost is much lower.

Complexity of Randomised Algorithms

Definition — Expected Complexity
For a randomised algorithm, the running time TA(I) is a probability distribution (not a single value), since it depends on random choices made during execution.

The expected (worst-case) time complexity is: maxI ∈ I(n) E[TA(I)]

This takes the maximum over all inputs (worst case) while averaging over the algorithm's random choices. It is important not to conflate worst-case behaviour (depends on input) with unlucky random decisions (depends on the random choices made).

Lower Bound Complexity

Definition — Lower Bound Complexity
The lower bound complexity for a problem is the lowest possible complexity that any algorithm (known or unknown) can achieve to solve the problem. Unless otherwise stated, lower bound is for worst-case complexity.

If an algorithm achieves the lower bound, it is called optimal.

Examples of lower bounds:

  • Finding minimum in an unsorted array: Lower bound is Ω(n), since every element must be examined at least once. The linear-scan algorithm achieves O(n), so it is optimal.
  • Comparison-based sorting: Lower bound is Ω(n log n). Any comparison-based sorting algorithm must make at least Ω(n log n) comparisons in the worst case (proved via a decision tree argument — not examinable). Merge Sort and Heap Sort achieve O(n log n), making them optimal among comparison-based sorts.

Comparison Cost

We typically assume comparisons take O(1) time. However, this is not always true:

  • String comparison: Comparing two strings of length L takes O(L) in the worst case — strings are compared character-by-character from left to right until a difference is found. E.g., comparing "Welcome to Faculty of IT" and "Welcome to FIT2004" requires comparing all characters up to the first difference.
  • Number comparison: For machine-word sized integers (fitting in a register), comparison is O(1). For very large numbers (e.g., in arbitrary-precision arithmetic), comparison would be O(digits).
Convention in This Unit
  • String comparison costs O(c), where c is the number of characters compared.
  • Numerical comparison costs O(1) unless otherwise specified.

§ 1.1 Proving Algorithm Correctness

Testing detects inputs for which a program gives incorrect output, but cannot test all inputs (there are infinitely many). Testing cannot guarantee correctness. Logic can. A correctness proof has two parts:

  1. Termination: Show that the algorithm always halts in finite time.
  2. Correctness at termination: Show that when it halts, it produces the right answer.

Loop Invariants

Definition — Loop Invariant
A loop invariant is a statement about the algorithm's state that is true at three critical points:
  1. Initialisation: True before the loop starts.
  2. Maintenance: If true at the beginning of an iteration, it remains true at the beginning of the next iteration.
  3. Termination: When the loop terminates, the invariant (combined with the reason the loop stopped) gives us the correctness result.

Example — Find Minimum (Loop Invariant)

min = array[1]
index = 2
// Loop Invariant: min equals the minimum value in array[1 ... index-1]
while index <= N:
    if array[index] < min:
        min = array[index]
    index = index + 1
return min
  • Initialisation: Before the loop, index = 2, and array[1..1] = {array[1]}, whose minimum is min = array[1]. ✓
  • Maintenance: Assume LI is true at index = k (min = min of array[1..k-1]). After the iteration, we compare array[k] with min and update min if necessary. So min = min of array[1..k], which means LI holds at index = k+1. ✓
  • Termination: Loop exits when index = N+1. LI gives: min = min of array[1..N]. ✓

Example — Selection Sort (Loop Invariant)

// LI: arr[1..i-1] is sorted AND arr[1..i-1] <= arr[i..N]
for i = 1 to N-1:
    j = index of minimum element in arr[i..N]
    swap(arr[i], arr[j])
// At termination i = N: arr[1..N-1] sorted AND arr[1..N-1] <= arr[N]
// Therefore arr[1..N] is fully sorted.
Why Selection Sort Needs Both Invariant Conditions
The invariant for selection sort requires two conditions: (1) the sorted prefix is sorted, and (2) everything in the sorted prefix is ≤ everything in the unsorted suffix.

If only condition (1) were maintained (as in Insertion Sort's invariant), it would break: after swapping the minimum of arr[i..N] into position i, the sorted prefix arr[1..i-1] might receive a value smaller than arr[i-1], violating "is sorted". The stronger invariant (both conditions) is needed.

Example — Binary Search (Loop Invariant and Termination Proof)

For the binary search that finds the rightmost instance of a target:

Invariant: If the target is in the list, its rightmost instance is in L[lo..hi-1].

// Invariant: if target is in L, it is in L[lo..hi-1]
lo = 1
hi = N + 1
while lo < hi - 1:
    mid = floor((lo + hi) / 2)
    if target >= L[mid]:
        lo = mid        // target is at or right of mid
    else:               // target < L[mid]
        hi = mid        // target is left of mid (L[hi] is excluded)
if L[lo] == target:
    return lo
return False

Termination proof:

  • Since lo < hi - 1, we have lo ≤ hi - 2. Therefore mid = floor((lo+hi)/2) satisfies lo < mid < hi (proven rigorously in the course notes using the floor inequality).
  • When we set lo = mid, lo strictly increases by at least 1. When we set hi = mid, hi strictly decreases by at least 1.
  • So every iteration, hi - lo decreases by at least 1. Since this is finite, the loop must terminate.

Correctness proof:

  • Init: L[lo..hi-1] = L[1..N] = entire list. If target exists, it's here. ✓
  • Maintenance: If target is in L[lo..hi-1] and we check L[mid]:
    • If target ≥ L[mid]: target could be at mid or to its right, so set lo = mid. ✓
    • If target < L[mid]: target is strictly left of mid, so set hi = mid (hi is exclusive). ✓
  • Termination: lo = hi - 1, so only L[lo] remains. Return lo if found, False otherwise. ✓

Ch. 2 Divide and Conquer

The Divide and Conquer algorithm design paradigm is one of the most important and powerful techniques in algorithm design. It works by breaking a large problem into smaller, more manageable subproblems, solving those subproblems, and then combining their solutions.

Definition — Divide and Conquer Paradigm
A divide-and-conquer algorithm works in three steps:
  1. Divide: Break the problem into smaller subproblems of the same type.
  2. Conquer: Solve the subproblems recursively. At the base case (when the subproblem is small enough), solve directly.
  3. Combine: Merge the solutions of the subproblems to produce the solution to the original problem.
Analysing the time complexity of a D&C algorithm normally involves solving a recurrence relation. Normally a polynomial-time solution to the problem is already known, and D&C is used to reduce the time complexity to a lower polynomial.

Applications of Divide and Conquer

  • Karatsuba's multiplication: O(n1.585) — covered in detail below
  • Merge Sort: O(n log n) — covered below
  • Counting Inversions: O(n log n) — covered below
  • Closest pair of points in a plane: O(n log n)
  • Strassen's matrix multiplication: O(n2.807) — sub-cubic
  • Fast Fourier Transform (FFT): O(n log n) — extremely influential, used in signal processing, audio, image compression, polynomial multiplication

§ 2.1 Karatsuba's Multiplication Algorithm

The Problem

Problem: Multiply two n-digit numbers x and y, using only addition, subtraction, and multiplication of single-digit numbers as basic operations.

The grade school algorithm (multiplying using partial products) clearly takes O(n²) time: for each of the n digits of y, we multiply it by all n digits of x, producing n partial products, then sum them up.

First Improvement Idea — Split into Halves

A natural divide-and-conquer approach is to split each number at its midpoint:

  • Let xM = the n/2 most significant digits of x
  • Let xL = the n/2 least significant digits of x
  • Let yM = the n/2 most significant digits of y
  • Let yL = the n/2 least significant digits of y

Then:

Mathematical Decomposition
x = xM · 10n/2 + xL
y = yM · 10n/2 + yL

x · y = xM·yM·10n + (xM·yL + xL·yM)·10n/2 + xL·yL

Note: multiplications by powers of 10 are trivial left shifts, costing O(n).

This naive approach requires four recursive calls (computing xM·yM, xM·yL, xL·yM, xL·yL), giving the recurrence T(n) = 4T(n/2) + c·n. By the Master Theorem (case 1: nlog24 = n² dominates cn), this resolves to O(n²) — no improvement!

Why 4 Recursive Calls Doesn't Help
With 4 calls each of size n/2: the work at each level stays approximately constant. At each level we do O(n) combining work and have 4× as many subproblems each of half the size — the total work per level actually grows, yielding O(n²) overall. To improve, we need at most 3 recursive calls.

Karatsuba's Key Insight — The Gauss Trick

For decades, no sub-quadratic multiplication algorithm was known. Russian mathematician Andrey Kolmogorov (20th century giant in probability and complexity theory) even conjectured that sub-quadratic multiplication was impossible. Then Anatoly Karatsuba, a 23-year-old student, heard the conjecture at Kolmogorov's seminar and within one week produced the counter-example.

The key observation is that we need the term z = xM·yL + xL·yM. Instead of computing this directly with two multiplications, we use only three multiplications total:

Karatsuba's Trick
Compute only these three products:
  1. a = xM · yM    (1st recursive call)
  2. b = xL · yL    (2nd recursive call)
  3. c = (xM + xL) · (yM + yL)    (3rd recursive call)

Then observe that:
(xM + xL)·(yM + yL) = xM·yM + (xM·yL + xL·yM) + xL·yL
c = a + z + b
Therefore: z = c − a − b

We obtain the missing cross-term z with zero additional multiplications — just two subtractions!
Historical Origin — Gauss's Method for Complex Numbers
This trick traces back to Gauss's method for multiplying complex numbers (a + bi)(c + di) using only 3 real multiplications instead of 4:
Compute ac, bd, and (a+b)(c+d). Then the real part is ac − bd and the imaginary part is (a+b)(c+d) − ac − bd.

Adapting previous ideas to solve new problems is one of the most valuable skills in algorithm design.

Karatsuba's Algorithm — Pseudocode

Algorithm: Karatsuba(x, y) — sub-quadratic integer multiplication T(n) = O(n^log₂3) ≈ O(n^1.585) 
function KARATSUBA(x, y):
    // x and y are n-digit positive integers
    if n = 1:
        compute x * y in one step and return the result

    // Split x and y at the midpoint
    x_M, x_L = first half, second half of x (each n/2 digits)
    y_M, y_L = first half, second half of y (each n/2 digits)

    // Three recursive calls (each on n/2-digit numbers)
    a = KARATSUBA(x_M, y_M)                    // x_M * y_M
    b = KARATSUBA(x_L, y_L)                    // x_L * y_L
    u = x_M + x_L                              // grade school addition: O(n)
    v = y_M + y_L                              // grade school addition: O(n)
    c = KARATSUBA(u, v)                        // (x_M + x_L) * (y_M + y_L)

    // Combine: z = c - a - b = x_M*y_L + x_L*y_M
    z = c - a - b                              // grade school subtraction: O(n)

    // Result: a * 10^n  +  z * 10^(n/2)  +  b
    return a * 10^n + z * 10^(n/2) + b        // left shifts + addition: O(n)

Complexity Analysis of Karatsuba's Algorithm

Complexity — Karatsuba's Algorithm
Recurrence: T(n) = 3T(n/2) + c·n

The 3 comes from the three recursive calls; the c·n comes from the grade school addition/subtraction operations and the left-shift combining step, all of which are linear.

Solution: By the Master Theorem (case 1, since nlog23 ≈ n1.585 dominates cn = n1):
T(n) = Θ(nlog23) = O(n1.585)

where log23 ≈ 1.585.

Compared to grade school: O(n1.585) vs O(n²). For n = 1,000,000 digits, this is a factor of roughly n0.415 ≈ 40,000× improvement!
Practical Significance
Karatsuba's algorithm is what Python uses internally to multiply large integers. The difference between n² and n1.585 is dramatic for large inputs — do not underestimate improvements in the exponent of polynomial algorithms.

Why T(n) = 4T(n/2) + cn Gives O(n²)

For comparison, with 4 recursive calls: by the Master Theorem, nlog24 = n² dominates cn, so T(n) = Θ(n²). No improvement over grade school. The key insight is that reducing from 4 to 3 recursive calls changes the base of the exponent from log24 = 2 to log23 ≈ 1.585, a significant improvement.

§ 2.2 Merge Sort (Revision)

Merge sort is a divide-and-conquer sorting algorithm presented by John von Neumann (one of the greatest mathematicians of the 20th century). It was one of the first explicit uses of the D&C paradigm. Python's standard sorted() function uses Timsort — a hybrid algorithm derived from Merge Sort and Insertion Sort.

The Three Steps

  1. Divide: Split the array in half at the midpoint.
  2. Conquer: Recursively sort each half. Base case: a single element is trivially sorted.
  3. Combine: Merge the two sorted halves into a single sorted array.

The Merge Subroutine

The core of merge sort is the merge routine, which takes two sorted arrays A and B and produces a single sorted output by interleaving them:

Algorithm: Merge(A[i..n1], B[j..n2]) — merging two sorted arrays Time: O(n) | Space: O(n) 
function MERGE(A[i..n1], B[j..n2]):
    result = empty array

    while i <= n1 OR j <= n2:
        // Take the smaller of the two front elements
        if j > n2  OR  (i <= n1 AND A[i] <= B[j]):
            result.append(A[i])   // Take from A
            i += 1
        else:
            result.append(B[j])   // Take from B
            j += 1

    return result
Stability of Merge
The merge routine is stable because we use A[i] ≤ B[j] (not strict less-than). When A[i] equals B[j], we prefer A (the left array), preserving the original relative order of equal elements. Since the merge is stable, the entire merge sort algorithm is also stable.

Merge Sort Pseudocode

Algorithm: Merge-Sort(array[lo..hi]) Time: O(n log n) | Aux Space: O(n) 
function MERGE_SORT(array[lo..hi]):
    if hi > lo:                              // More than one element
        mid = floor((lo + hi) / 2)
        MERGE_SORT(array[lo..mid])           // Recursively sort left half
        MERGE_SORT(array[mid+1..hi])         // Recursively sort right half
        array[lo..hi] = MERGE(array[lo..mid], array[mid+1..hi])  // Combine

Correctness of Merge Sort

The correctness of merge sort can be argued by induction on the size of the array:

  • Base case: An array of one element (lo = hi) is trivially sorted. No recursion occurs.
  • Inductive hypothesis: Assume MERGE_SORT correctly sorts any array of size < n.
  • Inductive step: For an array of size n, we split it into two halves of sizes roughly n/2. By the inductive hypothesis, MERGE_SORT correctly sorts each half. We then merge two sorted arrays — the MERGE routine produces a correctly sorted array from two sorted inputs (this can be proven by its own loop invariant). Therefore MERGE_SORT correctly sorts the full array.

Complexity Analysis of Merge Sort

Complexity — Merge Sort
Recurrence: T(n) = 2T(n/2) + c·n

The 2 comes from two recursive calls; the c·n comes from the MERGE step which processes all n elements linearly.

Solution: By the Master Theorem (case 2, since nlog22 = n1 = n = Θ(cn)):
T(n) = Θ(n log n) = O(n log n)

Intuition: There are log2(n) levels of recursion. At each level, the total work to merge all the subproblems is O(n) (since every element is touched once per level). So total work = O(n) × O(log n) = O(n log n).
Best Case Average Case Worst Case
Time O(n log n) O(n log n) O(n log n)
Auxiliary Space O(n) O(n) O(n)

Properties of Merge Sort

  • Stable: Yes — the MERGE routine preserves relative order of equal elements.
  • In-place: No — the MERGE step requires O(n) auxiliary space to store the output array. The merge sort call stack itself also uses O(log n) space for the recursion.
  • Optimal: Yes, among comparison-based sorting algorithms — it achieves the Ω(n log n) lower bound.
  • Consistent: Best, average, and worst case are all Θ(n log n) — merge sort has no "bad" inputs like quicksort does.

Enhancements of Merge Sort

  • Bottom-up merge sort: Eliminate recursion entirely by iteratively merging subarrays of size 1, 2, 4, 8, ..., n. Still O(n) auxiliary space but avoids call stack overhead. Slightly faster in practice.
  • In-place merge sort: There exist O(1) auxiliary space variants of merge sort, but they are significantly more complex to implement and typically slower in practice.
  • Timsort: Python's built-in sort, a hybrid of merge sort and insertion sort. Uses insertion sort for small runs (which are faster in practice due to low overhead) and merge sort to combine them. Also takes advantage of already-sorted runs in the input.

Stable Sorting — Why It Matters
A sorting algorithm is stable if it maintains the relative ordering of elements with equal keys.

Example: Sorting students by marks. If two students have the same marks, a stable sort preserves their original (alphabetical) ordering. An unstable sort may reorder them arbitrarily.

Multi-key sort technique: To sort by a primary key and use a secondary key as a tiebreaker, (1) first stable-sort by the secondary key, then (2) stable-sort by the primary key. The stability of step 2 ensures ties in the primary key retain the order established in step 1.

§ 2.3 Counting Inversions

Problem Definition and Motivation

Counting inversions is a fundamental algorithmic problem with applications in collaborative filtering (a technique used by recommender systems to measure how similar two users' preferences are). The more inversions exist between two rankings, the more dissimilar the preferences.

Definition — Counting Inversions Problem
Input: An array A of n distinct integers.
Output: The number of inversions in A, i.e., the number of pairs of indices (i, j) such that i < j and A[i] > A[j].

Informally, an inversion is a pair of elements that are "out of order" relative to the sorted sequence.
Intuition — Inversions and Similarity
If both users rank a set of movies the same way, there are 0 inversions. The more they disagree, the more inversions. A completely reversed ranking of n items has n(n−1)/2 = Θ(n²) inversions — the maximum possible.

Example: A = [2, 4, 1, 3, 5] has inversions: (2,1), (4,1), (4,3) → 3 inversions.

Naive O(n²) Approach

The brute force algorithm simply checks every pair:

Algorithm: Count-Inversions-Naive — brute force Time: O(n²) 
function COUNT_INVERSIONS_NAIVE(A[1..n]):
    count = 0
    for i = 1 to n:
        for j = i+1 to n:
            if A[i] > A[j]:
                count += 1
    return count

Since there may be Θ(n²) inversions in the worst case (a reversed array), a sub-quadratic algorithm cannot look individually at each inversion — it must count multiple inversions in a single step. This is exactly what the divide-and-conquer approach achieves.

The Key Idea — Augmented Merge Sort

The O(n log n) algorithm is an augmentation of merge sort. The insight is to classify inversions into three types based on where the two indices come from:

  • Left inversions: Both i and j are in the left half A[lo..mid].
  • Right inversions: Both i and j are in the right half A[mid+1..hi].
  • Split inversions: i is in the left half and j is in the right half (i < j by definition since all left indices < all right indices).

Left and right inversions are counted recursively. The challenge — and the key insight — is to count split inversions efficiently during the merge step.

Counting Split Inversions During Merge
When we merge two sorted halves A[lo..mid] and A[mid+1..hi], at each step we pick the smaller leading element. Suppose we pick element B[j] from the right array (rather than A[i] from the left):

This means A[i] > B[j]. But since the left array is sorted, it is also true that A[i+1], A[i+2], ..., A[n1] are all > B[j]. Therefore, B[j] forms a split inversion with all remaining elements in the left array.

If there are n1 − i + 1 elements remaining in the left array when we pick from the right, we add n1 − i + 1 to our split inversion count.

When we pick from the left array, no split inversions are counted (the left element is already smaller than all remaining right elements).

Sort-and-CountInv Algorithm

Algorithm: Sort-and-CountInv(array[lo..hi]) Time: O(n log n) | Aux Space: O(n) 
function SORT_AND_COUNT_INV(array[lo..hi]):
    if lo == hi:
        return (array[lo], 0)           // Base case: single element, 0 inversions
    else:
        mid = floor((lo + hi) / 2)

        // Recursively sort-and-count both halves
        (array[lo..mid], InvL)   = SORT_AND_COUNT_INV(array[lo..mid])
        (array[mid+1..hi], InvR) = SORT_AND_COUNT_INV(array[mid+1..hi])

        // Merge and count split inversions
        (array[lo..hi], InvS) = MERGE_AND_COUNT_SPLIT_INV(
                                    array[lo..mid], array[mid+1..hi])

        Inv = InvL + InvR + InvS
        return (array[lo..hi], Inv)

Merge-and-CountSplitInv Algorithm

Algorithm: Merge-and-CountSplitInv(A[i..n1], B[j..n2]) Time: O(n) per call 
function MERGE_AND_COUNT_SPLIT_INV(A[i..n1], B[j..n2]):
    result = empty array
    splitInversions = 0

    while i <= n1 OR j <= n2:
        if j > n2  OR  (i <= n1 AND A[i] <= B[j]):
            // Left element is smaller (or right exhausted): take from A
            result.append(A[i])
            i += 1
            // No split inversions counted here (A[i] <= all remaining B)

        else:
            // Right element is smaller: take from B
            result.append(B[j])
            j += 1
            // A[i], A[i+1], ..., A[n1] are ALL > B[j-1]
            // Each of these forms a split inversion with B[j-1]
            splitInversions += (n1 - i + 1)

    return (result, splitInversions)

Worked Example

Consider A = [6, 5, 4, 3, 2, 1] (maximum inversions — 15 pairs):

  • Split at mid: left = [6, 5, 4], right = [3, 2, 1]
  • Recursively sort left → [4, 5, 6] with InvL = 3 (pairs: (6,5), (6,4), (5,4))
  • Recursively sort right → [1, 2, 3] with InvR = 3 (pairs: (3,2), (3,1), (2,1))
  • Merge [4,5,6] and [1,2,3]:
    • Pick 1 from right: 3 left elements remain → InvS += 3
    • Pick 2 from right: 3 left elements remain → InvS += 3
    • Pick 3 from right: 3 left elements remain → InvS += 3
    • Pick 4,5,6 from left: no inversions counted
    • InvS = 9
  • Total = 3 + 3 + 9 = 15 ✓ (= n(n-1)/2 = 6×5/2 = 15)

Complexity Analysis

Complexity — Counting Inversions
Recurrence: Same as merge sort: T(n) = 2T(n/2) + O(n)

The O(n) combining step counts split inversions in linear time during the merge.

Solution: T(n) = O(n log n)

Space: O(n) auxiliary space for the merge step.

This is essentially merge sort with a running counter — the asymptotic complexity is identical to merge sort.
Why O(n log n) Is Remarkable
There are potentially Θ(n²) inversions in the input — a fully reversed array has n(n−1)/2 inversions. Yet we count all of them in O(n log n) time. The key is that during the merge step, we count many inversions at once: when a single right element B[j] is smaller than all k remaining left elements, we add k to the count in O(1) time.
