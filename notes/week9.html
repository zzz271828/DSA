Motivation Lookup Tables & The Problem with Plain BSTs

A lookup table (dictionary / dynamic set) supports three core operations: insert, search, and delete by key. An ordered array achieves O(log n) search via binary search, but insertion and deletion require O(n) shifting — we can do better.

A Binary Search Tree promises O(log n) for all three operations — but only when the tree is balanced. The critical weakness of a plain BST is that it can degenerate. If keys are inserted in sorted order, every new node is appended to the right, producing a structure indistinguishable from a linked list with height n.

Worst-Case Degeneration
Inserting keys 1, 2, 3, 4, 5, … in order into a plain BST produces a right-skewed linked list of height n. Search, insert, and delete all become Θ(n) in this case.

The solution studied in this chapter is to use self-balancing BSTs — data structures that automatically restructure themselves after each modification to guarantee O(log n) height at all times.

§ 10.1 Binary Search Trees

The BST Property

Definition — Binary Search Tree
A Binary Search Tree is a rooted binary tree in which, for every node u with key k:
  • Every key in u's left subtree is strictly less than k.
  • Every key in u's right subtree is strictly greater than k.
Keys are assumed to be unique. Nodes typically store a key-value pair; we focus on keys.

A direct consequence of this property is that an inorder traversal (visit left subtree, then current node, then right subtree) of any BST visits keys in non-decreasing sorted order. This means a BST implicitly maintains a sorted sequence.

Example BST

         10
        /  \
       7    20
      / \   / \
     3   9 14  33
    / \ / \   / \
   1  5 8  12 31  37
       \       \
        (...)  28
                \
                27

Core Operations

Search

Starting at the root, compare the target key k against the current node's key r:

  • If k = r: key found.
  • If k < r: recurse into the left subtree.
  • If k > r: recurse into the right subtree.
  • If we reach a NULL: key not in tree.
BST-Search(node, k) O(h) — h = height of tree 
BST-Search(node, k):
    if node == NULL:
        return NULL          // key not found
    if k == node.key:
        return node          // found
    elif k < node.key:
        return BST-Search(node.left, k)
    else:
        return BST-Search(node.right, k)

Insert

Perform a search for the key. If not found, insert a new node at the NULL position where the search terminated.

BST-Insert(node, k) O(h) 
BST-Insert(node, k):
    if node == NULL:
        return new Node(k)   // create leaf
    if k < node.key:
        node.left = BST-Insert(node.left, k)
    elif k > node.key:
        node.right = BST-Insert(node.right, k)
    // if k == node.key: key already present, do nothing (or update value)
    return node

Delete

There are three cases depending on how many children the target node has:

  1. Leaf node (no children): Simply remove it.
  2. One child: Replace the node with its single child (promote the child).
  3. Two children: Find the inorder successor (smallest key in right subtree) or inorder predecessor (largest in left subtree). Swap the target's key with the successor/predecessor, then delete the successor/predecessor (which has at most one child — the right case then recurses into case 1 or 2).
BST-Delete(node, k) O(h) 
BST-Delete(node, k):
    if node == NULL:
        return NULL
    if k < node.key:
        node.left = BST-Delete(node.left, k)
    elif k > node.key:
        node.right = BST-Delete(node.right, k)
    else:                        // k == node.key: delete this node
        if node.left == NULL:
            return node.right    // case 1 or case 2 (right child or NULL)
        elif node.right == NULL:
            return node.left     // case 2 (left child)
        else:
            // case 3: replace with inorder successor
            successor = BST-Minimum(node.right)
            node.key = successor.key
            node.right = BST-Delete(node.right, successor.key)
    return node

BST-Minimum(node):
    while node.left != NULL:
        node = node.left
    return node

Key Insight
The fundamental limitation of a plain BST is that its height is determined by insertion order, not by the number of elements. Two trees storing the same n keys can have heights ranging from ⌊log₂(n+1)⌋ (perfectly balanced) to n (completely skewed). Self-balancing trees solve this by enforcing a height bound of O(log n) after every operation.

§ 10.2 AVL Trees

The AVL Tree (named after Adelson-Velskii and Landis, 1962) was the first self-balancing BST ever invented. It enforces a strict local balance condition: at every node, the heights of the left and right subtrees differ by at most 1. This is sufficient to guarantee O(log n) height globally.

Definition and Balance Factor

Definition — AVL Tree
An AVL Tree is a BST in which, for every node u:

balance_factor(u) = height(u.left) − height(u.right)

and |balance_factor(u)| ≤ 1 (i.e., balance factor ∈ {−1, 0, 1}).

Convention: height(NULL) = 0. A node with no children has height 1 and balance factor 0.

Why O(log n) height? The tightest an AVL tree can pack nodes at each height is related to Fibonacci numbers. Let N(h) denote the minimum number of nodes in an AVL tree of height h. Then:

  • N(1) = 1, N(2) = 2
  • N(h) = N(h−1) + N(h−2) + 1 (the worst case: one subtree has height h−1, the other h−2)
  • This recurrence gives N(h) = Fib(h+2) − 1, where Fib is the Fibonacci sequence.
  • Since Fib(h) grows as φh/√5 (φ ≈ 1.618), we get n ≥ N(h) ∼ φh, so h = O(log n).
Height Bound
The height of an AVL tree with n nodes is Θ(log n). More precisely, the height is at most 1.44 · log₂(n+2) − 0.328.

In practice, storing the height at each node (rather than the balance factor directly) is much easier to maintain after rotations — just take max(height(left), height(right)) + 1 after each update. The balance factor is then computed on-demand.

Rotations — The Rebalancing Primitives

Rotations are local restructuring operations that change the shape of the tree while preserving the BST in-order property. They are the building blocks for all AVL (and Red-Black tree) rebalancing.

Left Rotation (of node x)

Used when x is right-heavy. y = x.right is promoted; x becomes y's left child. y's original left subtree (ST2) is rehomed as x's right subtree.

    BEFORE            AFTER
      x                 y
     / \               / \
   ST1   y           x   ST3
        / \          / \
      ST2 ST3      ST1  ST2

  x's left  (ST1) stays left of x.
  y's right (ST3) stays right of y.
  y's left  (ST2) becomes right of x.
  y is promoted; x demoted to y's left child.
Left-Rotate(x) O(1) 
Left-Rotate(x):
    y = x.right
    x.right = y.left       // ST2 rehomed
    if y.left != NULL:
        y.left.parent = x
    y.parent = x.parent    // link y to x's old parent
    if x.parent == NULL:
        root = y
    elif x == x.parent.left:
        x.parent.left = y
    else:
        x.parent.right = y
    y.left = x             // x becomes y's left child
    x.parent = y
    // update heights
    x.height = 1 + max(height(x.left), height(x.right))
    y.height = 1 + max(height(y.left), height(y.right))

Right Rotation (of node y)

Mirror image of left rotation. x = y.left is promoted; y becomes x's right child. x's original right subtree (ST2) is rehomed as y's left subtree.

    BEFORE            AFTER
      y                 x
     / \               / \
    x  ST3           ST1   y
   / \                    / \
 ST1 ST2               ST2  ST3

  x's left  (ST1) stays left of x.
  y's right (ST3) stays right of y.
  x's right (ST2) becomes left of y.
  x is promoted; y demoted to x's right child.
Right-Rotate(y) O(1) 
Right-Rotate(y):
    x = y.left
    y.left = x.right       // ST2 rehomed
    if x.right != NULL:
        x.right.parent = y
    x.parent = y.parent
    if y.parent == NULL:
        root = x
    elif y == y.parent.right:
        y.parent.right = x
    else:
        y.parent.left = x
    x.right = y
    y.parent = x
    // update heights
    y.height = 1 + max(height(y.left), height(y.right))
    x.height = 1 + max(height(x.left), height(x.right))

The Four Imbalance Cases

An imbalance occurs whenever a node's balance factor reaches +2 or −2. There are exactly four cases, determined by the imbalanced node's balance factor and its relevant child's balance factor. Rebalancing is always done bottom-up, starting from the deepest imbalanced node.

Why Bottom-Up?
Fixing a low-level imbalance may automatically fix a higher-level imbalance — redundant rotations are avoided. Always rebalance the deepest node first.

Case 1: Left-Left (LL)

Imbalanced node y has balance_factor = +2, and its left child x has balance_factor ∈ {0, 1}. The tree is left-heavy at both levels. Fix: a single right rotation on y.

                     if x was bf=1 → x becomes 0,  y becomes 0.

Case 2: Left-Right (LR)

Imbalanced node z has balance_factor = +2, and its left child x has balance_factor = −1. The tree is left-heavy at z but right-heavy at x. Fix: left rotation on x (converts to LL case), then right rotation on z.

Case 3: Right-Right (RR)

Mirror of LL. Imbalanced node has balance_factor = −2, right child has balance_factor ∈ {0, −1}. Fix: single left rotation on the imbalanced node.

Case 4: Right-Left (RL)

Mirror of LR. Imbalanced node has balance_factor = −2, right child has balance_factor = +1. Fix: right rotation on right child (converts to RR), then left rotation on imbalanced node.

Insert and Delete

AVL Insert

Insertion into an AVL tree proceeds in two phases:

  1. Standard BST insert: Find the correct leaf position and insert the new node.
  2. Rebalance pass (bottom-up): Walk up the tree from the inserted node toward the root. At each ancestor, update the stored height and check the balance factor. If a violation is found (|bf| = 2), apply the appropriate rotation (one of the four cases above). After the rotation, the subtree's height is restored to what it was before the insertion, so at most one rotation (single or double) is needed and the walk can stop.
AVL-Insert(root, k) O(log n) 
AVL-Insert(root, k):
    // Phase 1: BST insert
    node = BST-Insert(root, k)    // standard BST insert
    // Phase 2: walk up and rebalance
    current = node.parent
    while current != NULL:
        update_height(current)
        bf = balance_factor(current)
        if bf == 2:               // left-heavy
            if balance_factor(current.left) >= 0:  // LL case
                Right-Rotate(current)
            else:                                    // LR case
                Left-Rotate(current.left)
                Right-Rotate(current)
            break                 // at most 1 rotation restores balance
        elif bf == -2:            // right-heavy
            if balance_factor(current.right) <= 0:  // RR case
                Left-Rotate(current)
            else:                                     // RL case
                Right-Rotate(current.right)
                Left-Rotate(current)
            break
        current = current.parent

Insert Rotation Count
An AVL tree insert requires at most one rotation (single or double). After the rotation, the subtree height is exactly what it was before the insertion, so no further ancestors can be unbalanced.

AVL Delete

Deletion is more involved:

  1. Standard BST delete: Remove the target node using the standard three-case BST deletion procedure (leaf, one child, or replace with inorder successor).
  2. Rebalance pass (bottom-up): Walk up from the physically deleted node's parent (or the successor's original position) to the root. At each node, update heights and rebalance if needed. Unlike insert, deletion may require O(log n) rotations because each rotation can reduce a subtree's height, potentially unbalancing an ancestor further up.
Delete vs Insert — Rotation Count
Insert: at most 1 rotation (single or double). Delete: potentially O(log n) rotations — one per level on the path from deletion site to root.

§ 10.3 2-3 Trees

Invented by John Hopcroft (Turing Award, 1986) in 1970, a Perfectly Balanced 2-3 Search Tree (or simply 2-3 Tree) achieves a different kind of balance: all leaves are at the same depth. Instead of restructuring the tree after each modification, it allows nodes to temporarily expand, then splits them back into legal size. The tree grows upward (a new root is created when the root overflows) rather than downward.

2-3 trees are a special case of B-Trees (order 3), which generalise to larger node capacities for disk-based storage. They are also the conceptual foundation for Red-Black Trees.

Node Types

2-Node
Contains one key K and has two children:
  • Left subtree: all keys < K
  • Right subtree: all keys > K
Identical to a standard BST node.
3-Node
Contains two keys K1 < K2 and has three children:
  • Left subtree: all keys < K1
  • Middle subtree: all keys with K1 < key < K2
  • Right subtree: all keys > K2
Perfectly Balanced 2-3 Search Tree
A tree whose nodes are all 2-nodes or 3-nodes, and in which all leaves are at the same depth.

Example 2-3 Tree

            [11]
           /    \
        [4,7]   [25,31]
       /  |  \   /   |  \
     [2] [5] [8,9] [14] [20] [28] ...
                  (leaves all at same depth)

Searching in a 2-3 Tree

The search procedure is a natural generalisation of BST search. At each node:

  • If the node is a 2-node with key K: compare with K, go left or right.
  • If the node is a 3-node with keys K1, K2: compare with K1 and K2 to determine which of the three subtrees to recurse into.

Insertion

Insertion in a 2-3 tree never adds a leaf at the bottom directly — instead it always modifies existing nodes and propagates changes upward. The tree grows at the top, not the bottom.

Step 1: Search for the key to find the leaf it would land in.

Step 2 (at the leaf):

  • Leaf is a 2-node: Add the key to turn the leaf into a 3-node. Done.
  • Leaf is a 3-node: Temporarily create a 4-node (3 keys, 4 children). This is illegal and must be fixed.

Step 3 (fixing a 4-node): Split the 4-node — the middle key is promoted to the parent, and the 4-node becomes two 2-nodes.

  • If the parent was a 2-node, it becomes a 3-node — done.
  • If the parent was a 3-node, it becomes a 4-node — recurse upward.
  • If the 4-node is the root: create a new root containing the middle key, with the two halves as children. The tree grows by one level.
Key Insight — Growth Direction
In a plain BST, the tree grows at the bottom (new leaves are added). In a 2-3 tree, the tree grows at the top — a new root is created when the root overflows. This is why all leaves always remain at the same depth.
Insert-23Tree(tree, k) O(log n) 
Insert-23Tree(tree, k):
    leaf = Search-23Tree(tree.root, k)
    if k already in tree: return (or update value)

    add key k to leaf (temporarily creating a 4-node if needed)

    node = leaf
    while node is a 4-node:
        split(node):
            mid = middle key of node
            left_half  = new 2-node with left key
            right_half = new 2-node with right key
            promote mid to node.parent
            replace node with left_half and right_half as children of parent
        node = node.parent (now possibly a 4-node itself)

    if tree.root is a 4-node:
        split root: create new root with mid,
                    left and right halves as children

Deletion

Deletion preserves the "all leaves at same depth" invariant using the following strategy: ensure the node being visited on the way down is never a 2-node (i.e., has at least 2 keys). This way, when we reach the target, we can safely delete one key without creating an empty (0-key) node.

Case: Deleting a Leaf Key

The main idea is to maintain the invariant on the way down — the node currently being visited is not a 2-node. Use one of three fixes when a 2-node is encountered:

  1. Root merging: If root and both children are 2-nodes, merge them into a single 4-node (tree height decreases by 1).
  2. Rotation (borrow from sibling): If the current child is a 2-node but its immediate sibling is not, rotate the smallest sibling key into the parent and the smallest parent key into the current child.
  3. Merge with sibling: If the current child and its immediate sibling are both 2-nodes, merge them with the separating key from the parent into a 4-node and proceed into it.

After reaching the leaf and deleting the key, undo any remaining temporary 4-nodes on the way back up.

Case: Deleting an Internal Key

Navigate down to the key while maintaining the invariant. When the key is found in an internal node, continue down to its inorder successor (smallest key in the right subtree), while still maintaining the invariant. Swap the target key with the successor, then delete the successor from the leaf.

Deletion Guarantee
By maintaining the invariant that every visited node has ≥ 2 keys, we guarantee the leaf we ultimately delete from is not a 2-node — so no "underflow" occurs and the tree remains valid.

Height and Complexity

Height of a 2-3 Tree
All leaves are at depth h. The minimum number of nodes m satisfies m ≥ 2h+1 − 1 (the all-2-nodes case). Therefore h = O(log m). Since n ≥ m:

h = O(log n) — the height is logarithmic regardless of insertion order.
2-3 Tree Complexity
OperationTimeNotes
SearchO(log n)1 node per level, O(1) work each
InsertO(log n)1 pass down + ≤ 1 pass up
DeleteO(log n)1 pass down + 1 pass up

Practical Limitation
2-3 trees are elegant in theory but have two types of nodes with different structures. This creates many cases in implementation (the node type changes during splits and merges), making the code complex and introducing constant-factor overhead. Red-Black Trees encode the same structure in a standard BST, avoiding this complexity.

§ 10.4 Red-Black Trees

Red-Black Trees (first introduced by Guibas and Sedgewick in 1978) encode the structure of a 2-3 tree inside a plain BST using a single bit of colour information per node. This course focuses on the Left-Leaning Red-Black Tree (LLRBT) variant introduced by Sedgewick in 2008, which has a clean one-to-one correspondence with 2-3 trees.

Definition — Left-Leaning Red-Black Tree

Definition — Left-Leaning RBT (LLRBT)
A Left-Leaning Red-Black Tree is a BST where nodes/edges are coloured black or red such that:
  1. The colour of a non-root node equals the colour of its single incoming edge. The root is always black.
  2. All red links lean left — every red link goes to a left child.
  3. No node has two consecutive red links — no red node has a red child.
  4. Perfect black balance — for any node, the number of black edges on every path to a descendant leaf is the same.
The black height of the tree is the number of black edges between the root and any leaf.
Colour Encoding
The colour is stored as a single bit inside the node (not on the edge). The colour of a node is defined as the colour of its incoming edge (the edge from its parent). The root has no incoming edge, so it is defined to be black. This single bit determines the entire structure.

Height Bound

The black height of an LLRBT equals the height of the corresponding 2-3 tree, which is O(log n). Since no two consecutive red edges exist, any root-to-leaf path has at most twice the black height in total edges. Therefore:

LLRBT Height
The height of an LLRBT with n keys is O(log n). More precisely, height ≤ 2 · black_height + 1 ≤ 2 · log₂(n+1) + 1.

Equivalence with 2-3 Trees

There is an exact one-to-one correspondence between LLRBTs and 2-3 Trees. To convert a 2-3 tree to an LLRBT:

  1. For every 3-node [K1, K2]: separate it into two nodes. K2 becomes the BST node; K1 becomes K2's left child with a red edge.
  2. All original inter-node edges become black.
  3. Children of the 3-node are redistributed: left and middle children of K1 stay; middle child of K2's original 3-node becomes K1's right child; right child stays K2's right child.
  4. Unflatten so all edges point downward.
2-3 tree 3-node:          LLRBT encoding:

    [K1, K2]                    K2 (black)
   /   |    \          →       /
 L    M      R               K1 (RED)
                             /  \
                            L    M
                        (right child R stays with K2)

The reverse: to read a 3-node out of an LLRBT, find any black node with a red left child — together they form a 3-node.

2-3 Tree NodeLLRBT Representation
2-node (1 key)Black node with no red child
3-node (2 keys)Black node with a red left child
(Temporary) 4-node (3 keys)Black node with two red children (illegal — triggers rebalancing)

Insertion

Insertion produces the same end result as 2-3 tree insertion, expressed in LLRBT operations.

Step 1: Insert as a Red Node

Search for the key. If not found, insert a new node with a red edge/colour. This preserves perfect black balance (a red node doesn't change black-edge counts on any path). However, it may violate other LLRBT properties.

Step 2: Walk Up and Apply the Adjustment Procedure

Moving from the insertion point upward to the root, at each node apply these checks in order:

LLRBT Adjustment Procedure (per node, bottom-up)
  1. Condition 1 — Right-leaning red: If the node has only one red child and it is the right child → Left-Rotate the node. (Red links must lean left.)
  2. Condition 2 — Two consecutive left reds: If the left child is red and the left child's left child is also red → Right-Rotate the node. (No two consecutive reds.)
  3. Condition 3 — Both children red: If both children are red → Flip colours of the node and both children. (Equivalent to promoting the middle key of a 4-node in the 2-3 tree.)
  4. Condition 4 (optional early stop): If the current node is black and none of conditions 1–3 fired, stop (no further adjustments needed).
  5. Condition 5: If the current node is the root, paint it black.
LLRBT-Insert(root, k) O(log n) 
LLRBT-Insert(root, k):
    root = insert_rec(root, k)
    root.colour = BLACK          // Condition 5

insert_rec(node, k):
    if node == NULL:
        return new Node(k, RED)  // insert as red leaf

    if k < node.key:
        node.left = insert_rec(node.left, k)
    elif k > node.key:
        node.right = insert_rec(node.right, k)
    // else: k == node.key → already exists, no change

    // Apply adjustment conditions bottom-up (on the way back up the recursion)
    if is_red(node.right) and not is_red(node.left):   // Condition 1
        node = Left-Rotate(node)
    if is_red(node.left) and is_red(node.left.left):   // Condition 2
        node = Right-Rotate(node)
    if is_red(node.left) and is_red(node.right):       // Condition 3
        Flip-Colours(node)

    return node

is_red(node):
    return node != NULL and node.colour == RED

Flip-Colours(node):
    node.colour        = RED
    node.left.colour   = BLACK
    node.right.colour  = BLACK

The Three Insertion Sub-Cases (into a 2-node and a 3-node)

Inserting into a 2-node:

  • New key inserted as left child: No violation — left-leaning red link already correct. No adjustment needed.
  • New key inserted as right child: Condition 1 fires → Left-Rotate. Now the new red link leans left. Done.

Inserting into a 3-node (black node B with red left child A):

  • New key is largest (inserted as right child of B): Both children of B are now red → Condition 3: Flip colours. B turns red (promotes up), A and new node turn black.
  • New key is smallest (inserted as left child of A): Two consecutive left reds → Condition 2: Right-Rotate B → now both children red → Condition 3: Flip colours.
  • New key is between A and B (inserted as right child of A): Condition 1: Left-Rotate A → reduces to previous case (two consecutive left reds) → Condition 2 + 3.
Colour Flip = 4-Node Split in 2-3 Tree
The colour flip operation (both children red → parent becomes red, children become black) is exactly equivalent to the 4-node split in a 2-3 tree: the middle key is promoted to the parent, and the two outer keys become separate 2-nodes.

Worked Example: Inserting keys 27, 35, 10

Starting from existing LLRBT. Insert 27:
  → Inserted as red at leaf position under node 28.
  → No Condition fires at node 28. Done (Condition 4).

Insert 35:
  → At insertion point (node 33): Condition 1 fires → Left-Rotate(33).
  → At node 37: Condition 2 fires → Right-Rotate(37).
  → At node 35: Condition 3 fires → Flip-Colours(35).
  → At node 31: Condition 1 fires → Left-Rotate(31).
  → At node 35: Condition 4 holds. Done.

Insert 10:
  → At node 9: Condition 3 → Flip-Colours(9).
  → At node 7: Condition 3 → Flip-Colours(7).
  → At node 11: no condition fires.
  → At root node 25: Condition 2 → Right-Rotate(25).
  → At node 11: Condition 3 → Flip-Colours(11).
  → Node 11 is root → Paint black (Condition 5). Done.

Result matches exactly what 2-3 tree insertion produces.

Deletion

Deletion in an LLRBT mirrors deletion in a 2-3 tree. The core invariant maintained on the way down is: the current node being visited is not a 2-node (equivalently, it is red, or it has a red child). This ensures that when we reach the target key, we can delete it without creating an empty node.

The adjustment operations used on the way down include:

  • Move-Red-Left: When the current node's left child is a 2-node, borrow from the right — flip colours, then conditionally rotate.
  • Move-Red-Right: Mirror operation for moving right.
  • Balance: Apply the standard bottom-up conditions (same as insert) on the way back up.

For full implementation details, see Chapter 3 of Algorithms (4th edition) by Sedgewick & Wayne.

Why RBTs Are Used in Practice
While 2-3 trees are conceptually elegant, they require handling two different node types with many special cases. RBTs encode the same logical structure in a uniform BST — every node has exactly two child pointers plus one colour bit. This uniformity makes implementation cleaner and more cache-friendly in practice. Java's TreeMap and C++'s std::map both use Red-Black Trees internally.

§ 10.5 Comparing AVL and Red-Black Trees

Both AVL trees and Red-Black Trees (LLRBT) are self-balancing BSTs that guarantee O(log n) worst-case time for search, insert, and delete. They are asymptotically equivalent. The difference lies in concrete efficiency and the trade-off between read-heavy and write-heavy workloads.

Height and Strictness of Balance

AVL trees enforce a stricter balance condition (|balance_factor| ≤ 1 at every node) than RBTs. This leads to a smaller maximum height:

  • AVL: height ≤ 1.44 · log₂(n+2) ≈ 1.44 log n
  • RBT: height ≤ 2 · log₂(n+1) ≈ 2 log n

In absolute terms, an AVL tree is never taller than a Red-Black tree of the same size. A shorter tree means fewer comparisons per search — AVL trees win on pure lookup-intensive workloads.

Rotation Cost on Modifications

The cost of maintaining balance during insert and delete:

  • AVL Insert: at most 1 rotation (single or double). Very cheap.
  • AVL Delete: O(log n) rotations in the worst case. Can be expensive.
  • RBT Insert: at most 2 rotations + O(log n) colour flips. Rotations are cheap; colour flips are O(1) each but happen along the whole path.
  • RBT Delete: at most 3 rotations + O(log n) colour changes. Generally fewer restructuring operations than AVL delete.
Amortised Perspective
Although RBT insert can trigger O(log n) colour flips, colour flips are very cheap in practice (just setting a bit). The number of actual structural rotations is bounded by a small constant per operation in both trees when amortised. However, AVL trees need to update heights on every ancestor node during a rotation cascade, while RBTs can stop early (Condition 4 early-stop).

When to Use Which

  • Use AVL trees when the workload is heavily read-dominated (many more lookups than insertions/deletions). The stricter balance means shorter trees and fewer comparisons per search.
  • Use Red-Black Trees when the workload involves frequent insertions and deletions, or when writes and reads are balanced. Fewer structural changes per write operation makes RBTs faster in practice for mixed workloads. This is why almost every general-purpose ordered map in a standard library uses an RBT.
Real-World Usage
  • Java: TreeMap and TreeSet — Red-Black Tree.
  • C++ STL: std::map, std::set, std::multimap — Red-Black Tree.
  • Linux kernel: Completely Fair Scheduler (CFS) task queue — Red-Black Tree.
  • Python: sortedcontainers.SortedDict — B-Tree variant.
  • AVL trees appear in some database index implementations where lookup speed is critical.

Key Algorithmic Ideas to Remember

  1. BST inorder = sorted order. Any inorder traversal visits keys in ascending sequence.
  2. AVL balance factor ∈ {−1, 0, 1}. If |bf| = 2, rotate. Four cases: LL (right-rotate), LR (left-rotate child, right-rotate node), RR (left-rotate), RL (right-rotate child, left-rotate node).
  3. AVL insert ≤ 1 rotation; AVL delete ≤ O(log n) rotations.
  4. 2-3 tree grows at the top. New keys enter at leaves but the tree height increases only by adding a new root level — leaves stay at constant depth.
  5. LLRBT = 2-3 tree encoded in BST. Red left-link = two keys of a 3-node. Colour flip = 4-node split. The 3 adjustment conditions (rotate-left, rotate-right, flip) handle all insertion cases.
  6. RBT is used in practice. Uniform node structure and fewer rotation counts on writes make it the choice for real-world ordered map implementations.
