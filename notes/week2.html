Program Verification § 1.1

Program verification hinges on two main principles. First, we must prove that our algorithm, if it terminates, always produces the correct result (partial correctness). Second, we must prove that it does indeed always terminate (total correctness = partial correctness + termination).

Definition — Loop Invariant
A loop invariant is a statement about program variables that is true before the loop starts, remains true after every iteration of the loop, and at termination implies the correctness of the algorithm. It is a powerful tool for proving algorithm correctness formally.
Key Insight — Why Not Just Test?
Testing can detect incorrect outputs for specific inputs, but it cannot guarantee correctness for all inputs (there are infinitely many). Logic-based proofs via loop invariants give us that guarantee.

Three Steps of a Loop Invariant Proof

To prove correctness via a loop invariant, three things must be shown:

  1. Initialisation: The invariant holds before the loop begins (i.e., before the first iteration).
  2. Maintenance: If the invariant holds at the start of an iteration, it still holds at the start of the next iteration (the loop body preserves the invariant).
  3. Termination: When the loop terminates, the invariant (combined with the termination condition) implies the desired result — this is where correctness is established.

Motivating Example: Finding the Minimum

Before tackling binary search, consider a simple find-minimum algorithm:

Find Minimum O(n) 
function FIND_MIN(array[1..n])
    min = array[1]
    index = 2
    // LI: min equals the minimum value in array[1 .. index-1]
    while index <= n do
        if array[index] < min then
            min = array[index]
        index = index + 1
    return min

Invariant: min equals the minimum value of array[1..index-1].

  • Initialisation: Before the loop, index = 2, so array[1..index-1] = array[1..1]. min = array[1] is trivially the minimum of a single element. ✓
  • Maintenance: Assume the LI holds when index = k: min is the minimum of array[1..k-1]. After the iteration, we check array[k] and update min if smaller, then increment index to k+1. So min is now the minimum of array[1..k]. ✓
  • Termination: Loop terminates when index = n+1. The invariant then says min is the minimum of array[1..n] — exactly what we want. ✓

Binary Search — Key Example

Binary search is easy to get wrong — subtle off-by-one errors are common. The loop invariant approach gives us a systematic method to both design and verify the algorithm.

Binary Search (Course Notes Version) O(log n) 
function BINARY_SEARCH(array[1..n], key)
    lo = 1
    hi = n + 1
    while lo < hi - 1 do
        mid = floor((lo + hi) / 2)
        if key >= array[mid] then
            lo = mid
        else
            hi = mid
    if array[lo] == key then
        return lo          // key located at array[lo]
    else
        return null        // key not found
Loop Invariant — Binary Search
If key is in array, then at each iteration:
  1. array[lo] ≤ key
  2. If hi ≠ n+1, then array[hi] > key

Combined with the sortedness of the array, this implies that key (if it exists) lies within the range array[lo..hi-1].

Active subarray interpretation: lo is inclusive, hi is exclusive. The loop continues while the active subarray has more than one element (lo < hi - 1).

Proving Correctness: Case 1 — Key is in the Array

  • Initialisation: lo = 1, hi = n+1. Since the array is sorted, array[1] is the minimum, so array[lo] ≤ key. Part 2 is vacuously true since hi = n+1. ✓
  • Maintenance: At each step we compute mid = floor((lo+hi)/2) and compare array[mid] to key.
    • If key ≥ array[mid]: set lo = mid. Now array[lo] ≤ key still holds. ✓
    • If key < array[mid]: set hi = mid. Now array[hi] > key still holds. ✓
  • Termination: Loop exits when lo ≥ hi - 1. Combined with the invariant, this means lo = hi - 1, and the only candidate is array[lo]. If array[lo] = key, return lo; otherwise the key is absent. ✓

Proving Correctness: Case 2 — Key is NOT in the Array

Since key is not present, regardless of the termination value of lo, array[lo] ≠ key, and the algorithm correctly returns null. ✓

Design from Invariant
The invariant drives every design decision:
  • Why hi = n+1 initially? So the invariant holds vacuously.
  • Why lo < hi - 1 as the loop condition? The loop should continue as long as the active range has more than one element; it terminates when exactly one element remains.
  • Why lo = mid (inclusive) vs hi = mid (exclusive)? Because lo stores a valid lower bound candidate, while hi is the first excluded element.

Arguing Termination

We need to prove the algorithm terminates in finite time. The key theorem is that whenever lo < hi - 1, we have lo < mid < hi.

Theorem — Finiteness of Binary Search
If lo < hi - 1, then lo < mid < hi, where mid = floor((lo + hi) / 2).

Proof sketch: Since mid = floor((lo + hi)/2), we have (lo+hi)/2 - 1 < mid ≤ (lo+hi)/2. Because lo < hi - 1 implies lo ≤ hi - 2, algebraic manipulation yields lo < mid < hi.

Consequence: every iteration, either lo strictly increases or hi strictly decreases. The interval [lo..hi) is finite, so the loop must terminate.

Partial Correctness vs. Total Correctness

Definition
  • Partial correctness: If the algorithm terminates, it produces the correct answer. Proved by loop invariant (Initialisation + Maintenance + Termination steps).
  • Total correctness: Partial correctness plus the algorithm always terminates. Requires a separate termination argument (e.g., a decreasing function bounded below).

Strong vs. Weak Loop Invariants

A stronger invariant captures more information about the state. Selection sort uses a stronger invariant (sorted prefix and sorted prefix ≤ unsorted suffix), while insertion sort uses a weaker invariant (sorted prefix only). The invariant must be strong enough to prove the algorithm correct at termination.

Common Pitfall — Invariant Too Weak
If you use the weak invariant "arr[1..i-1] is sorted" for selection sort, you cannot prove maintenance: after swapping in the minimum of arr[i..n], the sorted prefix could be disrupted if the newly selected minimum is smaller than some element already in the prefix. The stronger invariant "arr[1..i-1] is sorted AND arr[1..i-1] ≤ arr[i..n]" is required.

Analysis of Basic Sorting Algorithms § 1.5

Selection Sort

Selection sort divides the array into a sorted prefix and an unsorted suffix. At each iteration, it finds the minimum of the unsorted suffix and swaps it into position at the boundary.

Algorithm 2 — Selection Sort O(n²) all cases 
function SELECTION_SORT(array[1..n])
    for i = 1 to n do
        min = i
        for j = i+1 to n do
            if array[j] < array[min] then
                min = j
        swap(array[i], array[min])
Loop Invariant — Selection Sort
For any value of i in the main loop, at the beginning of the iteration:
  1. array[1..i-1] is sorted.
  2. For any x in array[1..i-1] and y in array[i..n], x ≤ y.
This is a stronger invariant than insertion sort's. Both parts together are needed to prove correctness.

Correctness Proof

  • Initialisation: When i = 1, array[1..0] is empty — both invariants hold trivially. ✓
  • Maintenance: We find the minimum array[min] of array[i..n]. Since invariant 2 already ensures elements in the sorted prefix are ≤ all of array[i..n], swapping array[i] and array[min] maintains the sorted order of the extended prefix. The new minimum also satisfies invariant 2. ✓
  • Termination: When i = n, the invariant implies array[1..n] is sorted. ✓

Complexity Analysis

Selection sort always performs a complete scan of the unsorted portion on each iteration, regardless of the input's initial order. The number of comparisons is:

∑i=1n (n − i) = (n-1) + (n-2) + … + 1 + 0 = n(n-1)/2 = O(n²)

Average CaseO(n²)O(1)

Property
Selection sort performs at most n-1 swaps (one per outer loop iteration), which is useful when swapping is expensive. However, it always does O(n²) comparisons with no adaptation to input order. It is in-place (O(1) extra space), not stable (the swap may move equal elements out of relative order), not online, and non-adaptive.

Insertion Sort

Insertion sort also maintains a sorted prefix, but uses a weaker invariant than selection sort. At each iteration, it takes the next element from the unsorted portion and inserts it into its correct position in the sorted prefix by shifting elements rightward.

Algorithm 3 — Insertion Sort O(n) best, O(n²) worst 
function INSERTION_SORT(array[1..n])
    for i = 2 to n do
        key = array[i]
        j = i - 1
        while j > 0 and array[j] > key do
            array[j + 1] = array[j]
            j = j - 1
        array[j + 1] = key
Loop Invariant — Insertion Sort
For any value of i in the main loop, at the beginning of the iteration:
  1. array[1..i-1] is sorted.
This is a weaker invariant than selection sort. It does not guarantee that all elements in the sorted prefix are ≤ all elements in the unsorted suffix — they may not be.

Correctness Proof

  • Initialisation: When i = 2, array[1..1] is a single element — trivially sorted. ✓
  • Maintenance: At iteration i, we extract key = array[i] and shift elements in array[1..i-1] that are greater than key one position right, then place key. Since array[1..i-1] was sorted, after insertion, array[1..i] is sorted. ✓
  • Termination: The inner while loop terminates when either j = 0 or array[j] ≤ key. When the outer loop completes at i = n, the invariant guarantees array[1..n] is sorted. ✓

Complexity Analysis

  • Best case — already sorted input: The inner while loop never executes (each element is already ≥ its predecessor). Only the outer loop runs: O(n).
  • Worst case — reverse-sorted input: The inner while loop runs i-1 times for each i. Total: (1 + 2 + … + n-1) = O(n²). Same work as selection sort.
  • Average case: On average, about half the preceding elements need to be shifted. Still O(n²).
Why Insertion Sort is Fast for Nearly-Sorted Input
The number of operations is proportional to the number of inversions in the array — pairs (i, j) where i < j but array[i] > array[j]. A nearly-sorted array has very few inversions, so insertion sort runs in nearly O(n) time. This makes it the algorithm of choice for small arrays or arrays that are almost sorted (e.g., as a base case in hybrid sorts like Timsort).

Algorithm Properties

In-Place vs. Not In-Place

Definition — In-Place
An algorithm is in-place if it uses only O(1) auxiliary memory (i.e., constant extra space beyond the input). Both selection sort and insertion sort are in-place. Merge sort is not in-place (requires O(n) extra space).

Stable vs. Unstable

Definition — Stability
A sorting algorithm is stable if it preserves the relative ordering of elements that compare as equal.

Example: Sort students by mark. If Bill and Maria both scored 75, and Bill appears before Maria in the input, a stable sort guarantees Bill appears before Maria in the output as well.

Insertion sort is stable — elements are shifted, not swapped past equal elements.

Selection sort is not stable — the distant swap can change the relative order of equal elements.

Why Stability Matters
Stability enables multi-key sorting by composition:
  1. Sort by the secondary criterion first.
  2. Then stable-sort by the primary criterion.
The stable sort in step 2 preserves the secondary ordering for equal primary-key elements. This is also critical for Radix Sort, where each digit pass must be stable to preserve the ordering established by earlier (less-significant) digit passes.

Comparison-Based vs. Non-Comparison-Based

Definition
A comparison-based sort determines element order exclusively through pairwise comparisons (<, >, ≤, ≥, =, ≠). Examples: Selection Sort, Insertion Sort, Merge Sort, Heapsort, Quicksort. Non-comparison sorts exploit the structure of keys (e.g., integers in a range). Examples: Counting Sort, Radix Sort, Bucket Sort.

Adaptive vs. Non-Adaptive

Definition
An adaptive algorithm takes advantage of existing order in the input. Insertion sort is adaptive (runs in O(n) on sorted input). Selection sort is non-adaptive (always O(n²)).

Online vs. Offline

Definition
An online algorithm can process input sequentially without knowing the entire input in advance. Insertion sort is online: new elements can be inserted into an already-sorted prefix at any time. Selection sort is offline: adding new elements forces a restart because the algorithm scans the entire unsorted portion.

Comparison Cost Note

We typically assume comparing two numbers takes O(1) (machine-word-sized integers fit in a register). However, for strings, comparison is O(L) where L is the length of the shorter string — this becomes significant for genome sequences or long strings. The unit of analysis for comparison-based sorting is often the number of comparisons, which abstracts away the per-comparison cost.

Heapsort (Revision) § 3.1

The Binary Heap Data Structure

Definition — Binary Max-Heap
A binary max-heap is:
  • A complete binary tree: all levels are fully filled except possibly the last, which is filled from left to right.
  • Satisfies the max-heap property: every node is ≥ its children, so the maximum element is always at the root.

Array Representation

A complete binary tree can be stored compactly as a flat array array[1..n]:

  • Root is at array[1].
  • Children of node at index i are at indices 2i and 2i+1.
  • Parent of node at index i is at index floor(i/2).
  • The height of a heap with n nodes is O(log n), since the tree is complete.
Insight — Height is O(log n)
Because the tree is complete, the height is exactly floor(log₂(n)). This means all operations that traverse from a node to the root (RISE) or from the root to a leaf (FALL) take O(log n) time.

Heap Operations

RISE — Bubble Up

Used when a newly inserted or increased element may violate the heap property with its parent. Move it up until the property is restored.

Algorithm — RISE (max-heap) O(log n) 
function RISE(array[1..n], i)
    parent = floor(i / 2)
    while parent >= 1 do
        if array[parent] < array[i] then
            swap(array[parent], array[i])
            i = parent
            parent = floor(i / 2)
        else
            break

FALL — Bubble Down (Sift Down)

Used when the root is removed or an element is decreased. Move it down by swapping with the larger child until the property is restored.

Algorithm — FALL (max-heap) O(log n) 
function FALL(array[1..n], i)
    child = 2 * i
    while child <= n do
        // Pick the larger child
        if child < n and array[child + 1] > array[child] then
            child = child + 1
        if array[i] < array[child] then
            swap(array[i], array[child])
            i = child
            child = 2 * i
        else
            break

INSERT

Append new element to the end, then RISE it to restore the heap property.

Algorithm — INSERT O(log n) 
function INSERT(array[1..n], x)
    array.append(x)
    n += 1
    RISE(array[1..n], n)

EXTRACT_MAX (Delete Max)

Swap root with last element, remove last element, then FALL the new root to restore the heap property.

Algorithm — EXTRACT_MAX O(log n) 
function EXTRACT_MAX(array[1..n])
    swap(array[1], array[n])
    n = n - 1
    FALL(array[1..n], 1)
    return array.pop_back()    // returns the original maximum

HEAPIFY — Building a Heap in O(n)

Algorithm — HEAPIFY O(n) 
function HEAPIFY(array[1..n])
    for i = floor(n / 2) downto 1 do
        FALL(array[1..n], i)
Theorem — HEAPIFY Runs in O(n), Not O(n log n)

A naive analysis says HEAPIFY calls FALL (O(log n)) a total of n/2 times = O(n log n). But this is loose.

The key insight is that nodes near the bottom of the tree need very little work: a node at height h requires at most h swaps. There are approximately n/2h+1 nodes at height h. The total work is:

∑h=0log n (n / 2h+1) × h = O(n) ∑h=0∞ h/2h = O(n)

because the geometric series ∑h/2h converges to a constant (= 2). So HEAPIFY takes O(n) time, not O(n log n).

Heapsort Algorithm

Heapsort uses the heap data structure to sort in two phases: (1) heapify the array, (2) repeatedly extract the maximum and place it at the back of the array.

Algorithm 9 — Heapsort O(n log n) worst-case 
function HEAPSORT(array[1..n])
    HEAPIFY(array[1..n])             // O(n) -- build max-heap in-place
    for i = n downto 1 do
        array[i] = EXTRACT_MAX(array[1..i])
        // After iteration i: array[i..n] is sorted and contains the i largest elements

How It Works

  1. Call HEAPIFY to turn the array into a max-heap in O(n) time.
  2. For i = n down to 1: call EXTRACT_MAX on the heap of size i, which gives the current maximum. Place it at position array[i]. After this step, array[i..n] is sorted.
  3. After all n iterations, array[1..n] is sorted in ascending order.

Complexity

  • HEAPIFY: O(n)
  • n calls to EXTRACT_MAX, each taking O(log n): total O(n log n)
  • Overall: O(n log n)
Special Case — O(n) When All Elements Are Equal
If all elements are identical, each EXTRACT_MAX takes O(1) because no swaps are needed to restore the heap property after removing the root. Heapsort then runs in O(n) best case.
CaseTime ComplexityAuxiliary Space
Best CaseO(n)O(1)
Average CaseO(n log n)O(1)
Worst CaseO(n log n)O(1)

Properties of Heapsort

  • In-place: Yes. HEAPIFY is done in-place, and each EXTRACT_MAX places the element back in the array. O(1) auxiliary space.
  • Stable: No. Swaps during HEAPIFY and EXTRACT_MAX can move equal elements out of their original relative order.
  • Online: No. HEAPIFY requires the entire input to be known upfront.
  • Adaptive: No (for the most part). Heapsort always runs in O(n log n) regardless of input order.
  • Comparison-based: Yes. Subject to the O(n log n) lower bound.

Complexity Lower Bounds for Sorting § 3.3

Algorithms like mergesort, heapsort, and quicksort run in O(n log n). A natural question: can we do better than O(n log n)? For comparison-based algorithms, the answer is no.

Theorem — Lower Bound for Comparison-Based Sorting
Any comparison-based sorting algorithm requires Ω(n log n) comparisons in the worst case. No comparison-based algorithm can sort faster than O(n log n) in the worst case.

The Decision Tree Model

Definition — Decision Tree
A decision tree is a binary tree that models the execution of a comparison-based sorting algorithm on inputs of size n.
  • Each internal node represents a comparison of two elements.
  • Each branch (left/right) represents the outcome of that comparison.
  • Each leaf node represents a specific fully-sorted permutation of the input — the algorithm knows the complete sorted order when it reaches a leaf.
  • The worst-case number of comparisons equals the depth of the deepest leaf, i.e., the height of the tree.

Proof of the Lower Bound

The proof connects the structure of the decision tree to the factorial number of possible sorted orders.

Proof Sketch (not examinable in S1 2026)
  1. There are n! possible permutations of n elements. Each must correspond to a distinct leaf in the decision tree (the algorithm must be able to distinguish all possible orderings).
  2. A binary tree of height h has at most 2h leaves.
  3. Therefore: n! ≤ 2h, which gives h ≥ log₂(n!).
  4. We lower-bound log₂(n!): 
    log₂(n!) = log₂(1) + log₂(2) + ... + log₂(n)

Considering only the second half of terms (from n/2 to n):
≥ log₂(n/2) + log₂(n/2 + 1) + ... + log₂(n)
≥ (n/2) × log₂(n/2)
= (n/2) × (log₂(n) - 1)
= Ω(n log n)
  5. Hence the height of the tree is at least h = Ω(n log n), establishing the lower bound.

Stirling's Approximation (for context)

Stirling's Approximation

For large n:

n! ≈ √(2πn) × (n/e)n

Taking logarithms:

log₂(n!) = n log₂(n) − n log₂(e) + (1/2) log₂(2πn) = Θ(n log n)

This confirms that log₂(n!) = Ω(n log n), completing the lower bound proof.

Interpretation and Implications

What This Means
  • Merge sort, heapsort, and quicksort (average case) are optimal among comparison-based algorithms.
  • The lower bound applies to all comparison-based algorithms — known and unknown.
  • To beat O(n log n), we must use information beyond comparisons — i.e., exploit the structure of keys (as counting sort and radix sort do).
  • The lower bound is for worst-case. Some algorithms (like insertion sort) can achieve O(n) on nearly-sorted input, but their worst case is still ≥ Ω(n log n).
Definition — Lower Bound Complexity
The lower bound complexity of a problem is the lowest possible worst-case complexity that any algorithm (known or unknown) can achieve to solve the problem. A lower bound is important because it gives a theoretical limit on what is achievable.
  • Finding the minimum of n elements: Ω(n) (must inspect every element).
  • Comparison-based sorting of n elements: Ω(n log n).

Sorting Integers Fast § 3.4

The Ω(n log n) lower bound applies only to algorithms that use comparisons as their only operation on elements. If the keys have additional structure — specifically, if they are integers in a known bounded range — we can exploit that structure to sort faster.

Key Idea
Instead of asking "is A < B?", we can ask "what bucket does A belong to?". By counting occurrences and using positional arithmetic, we can place elements directly without comparisons.

Counting Sort

Suppose we want to sort an array whose elements are integers in the range 0 to u-1. Counting sort counts how many times each value occurs, then places each element into its correct position.

Intuition: Sorting 0s and 1s

As a simple example: to sort an array of only 0s and 1s, just count the number of 0s (say c) and write c zeros followed by n-c ones. This is O(n) — no comparisons needed. Counting sort generalises this idea to any integer range.

Stable Counting Sort Algorithm

The naive approach (write out count[v] copies of v) loses satellite data and is unstable. The stable version uses a position array (prefix sums) to place each element at its exact output index.

Algorithm 19 — Stable Counting Sort O(n + u) 
function COUNTING_SORT(array[1..n], u)
    // Phase 1: Count occurrences
    counter[0..u-1] = [0, 0, ...]
    for i = 1 to n do
        counter[array[i]] += 1

    // Phase 2: Compute starting positions (prefix sums)
    position[0..u-1] = [1, 0, ...]        // position[0] = 1 (1-indexed)
    for v = 1 to u-1 do
        position[v] = position[v-1] + counter[v-1]

    // Phase 3: Place elements into output (preserves stability)
    temp[1..n] = [0, 0, ...]
    for i = 1 to n do
        temp[position[array[i]]] = array[i]
        position[array[i]] += 1           // increment for next occurrence

    swap(array, temp)                      // copy result back

Step-by-Step Example

Input with key-value pairs: (3,a) (1,p) (3,c) (7,f) (5,g) (3,b) (7,d) (8,w)

  1. Phase 1 (count): count[1]=1, count[3]=3, count[5]=1, count[7]=2, count[8]=1
  2. Phase 2 (prefix sums): position[1]=1, position[3]=2, position[5]=5, position[7]=6, position[8]=8
  3. Phase 3 (place): Iterate through input left to right. For (3,a): place at position[3]=2, then increment position[3] to 3. For (1,p): place at position[1]=1. Continuing, the output is (1,p) (3,a) (3,c) (3,b) (5,g) (7,f) (7,d) (8,w).

Notice that the three elements with key 3 appear in the same relative order as in the input — (3,a), (3,c), (3,b) — confirming stability.

When is Counting Sort Linear?
  • Counting sort is O(n) if and only if u = O(n) (the universe size is proportional to the input size).
  • For w-bit integers: universe size u = 2w. Counting sort is linear iff w = O(log n).
  • Pitfall: If n=2 and u=263 (e.g., 64-bit integers), counting sort requires O(263) space — completely impractical.
Properties of Counting Sort
  • Stable: Yes (stable version). The iteration through input in order, combined with incrementing positions, preserves relative order.
  • In-place: No. Requires an auxiliary temp array of size n and a counter/position array of size u.
  • Comparison-based: No. Uses integer value as an index into the counter array.

Radix Sort

Counting sort becomes impractical when the value range is large (e.g., 64-bit integers). Radix sort extends counting sort to handle large integers by sorting digit by digit, using a small base so counting sort stays efficient.

Key Idea — LSD Radix Sort
Least Significant Digit (LSD) Radix Sort:
  1. Sort the array by the least significant digit (rightmost) using a stable sort.
  2. Sort by the second least significant digit, using a stable sort.
  3. Continue until the most significant digit (leftmost) is sorted.
Stability in each pass is critical: it preserves the ordering established by earlier (less-significant) digits.

Concrete Example (Base 10)

Sort: 7555, 4642, 3512, 1191, 1182, 5412, 1323, 6682, 9523, 6284, 3784, 9356

  1. Sort by 4th digit (units): 1191, 1182, 3512, 5412, 4642, 1323, 6682, 9523, 6284, 3784, 7555, 9356
  2. Sort by 3rd digit (tens) — stable: preserves relative order within same tens-digit groups
  3. Sort by 2nd digit (hundreds) — stable: …
  4. Sort by 1st digit (thousands) — stable: final sorted order
Why Stability is Essential
If the per-digit sort is unstable, later passes may scramble the ordering established by earlier passes. For example, after sorting by the units digit, two numbers with the same tens digit must retain their units-digit order. Only a stable sort guarantees this.

MSD (most-significant digit first) radix sort processes digits from left to right but requires a more complex implementation (recursive subproblems per bucket), whereas LSD naturally uses the stable counting sort subroutine.

Algorithm 20 — LSD Radix Sort O(d(n + b)) 
function RADIX_PASS(array[1..n], base, digit)
    counter[0..base-1] = [0, 0, ...]
    for i = 1 to n do
        counter[GET_DIGIT(array[i], base, digit)] += 1
    position[0..base-1] = [1, 0, ...]
    for v = 1 to base-1 do
        position[v] = position[v-1] + counter[v-1]
    temp[1..n] = [0, 0, ...]
    for i = 1 to n do
        d = GET_DIGIT(array[i], base, digit)
        temp[position[d]] = array[i]
        position[d] += 1
    swap(array, temp)

function RADIX_SORT(array[1..n], base, digits)
    for digit = 1 to digits do       // 1 = least significant
        RADIX_PASS(array[1..n], base, digit)

Complexity of Radix Sort

Suppose we sort n integers each with k digits in base b. Each RADIX_PASS is a counting sort over a universe of size b: O(n + b). There are k passes. Total:

CaseTime ComplexityAuxiliary Space
All CasesO(k(n + b))O(n + b)

Choosing the Optimal Base

For w-bit integers, the number of digits in base b is k = w / log(b), so the total complexity is:

O( (w / log(b)) × (n + b) )

Complexity Analysis — Choosing Base b = n

Each counting sort pass is O(n) as long as b = O(n). Setting b = n (base n):

  • Number of passes: k = w / log(n)
  • Cost per pass: O(n + n) = O(n)
  • Total: O( (w / log(n)) × n )

For integers with w = O(log n) bits (max value O(n)): complexity = O(n) — linear time!

More generally, for integers with w = c log(n) bits (max value O(nc)): complexity = O(cn) = O(n). This handles polynomially bounded integers in linear time — much better than counting sort, which could only handle values up to O(n).

Space complexity remains O(n) since b = n.

Applying Radix Sort to Strings

Strings can be sorted with radix sort by treating characters as digits. The radix (base) is the alphabet size (e.g., 26 for lowercase letters, 256 for ASCII). Use the character's ASCII value as the digit value: e.g., ord('A') = 65 in Python.

Properties of Radix Sort
  • Stable: Yes (when using stable counting sort as the subroutine).
  • In-place: No. Uses O(n + b) auxiliary space from counting sort.
  • Comparison-based: No. Keys are used as array indices.
  • Adaptive: No. All cases are O(k(n + b)).

The Fundamental Trade-off
  • Comparison-based sorts: flexible (work on any comparable data), but limited to Ω(n log n) worst case.
  • Non-comparison sorts: faster (O(n) possible), but require integer/structured keys and extra space.
  • In-place vs. stable: in general, achieving both simultaneously is very hard (e.g., stable in-place radix sort exists but is extremely complex).
