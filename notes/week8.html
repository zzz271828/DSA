§11.0 Motivation — Why Not BSTs or Hash Tables?

Suppose you have a large collection of N strings and you want to pre-process them so that future searches are fast. The standard approaches each have drawbacks:

Approach Pre-processing Search Key limitation
Sort + Binary Search O(MN log N) merge sort, or O(MN) radix sort O(M log N) Each string comparison costs O(M); logarithmic factor remains
BST (string keys) O(MN log N) O(M log N) At each BST node you pay O(M) for a full string comparison
Hash Table O(MN) O(M) expected No prefix queries; no deterministic worst-case; no sorted order
Prefix Trie O(|Σ| T) array-based O(M) Space can be large; O(|Σ| T) in worst case

Here M is the length of a single string, N is the number of strings, and T is the total number of characters across all strings. ReTrieval trees (tries) are designed to answer different queries efficiently — prefix matching, sorting, autocomplete — in time proportional only to the length of the query string, not to the number of strings stored.

§11.1 The Prefix Trie / Retrieval Tree

Definition — Prefix Trie
A prefix trie (retrieval tree) is a rooted, multi-way tree where:
  • Each edge is labelled with a character from the alphabet Σ.
  • Equivalently, each node (except the root) can carry the label of its incoming edge.
  • The path from the root to any node spells out a prefix of some string stored in the trie.
  • The path from the root to an internal node spells a common prefix shared by all strings in its subtree.
  • All strings sharing a prefix are stored within the same subtree — this is the defining structural property.

Terminal Marker $

Words are distinguished from mere prefixes by appending a special character $ (or equivalently, storing a boolean is_terminal flag at a node). Using $ ensures that:

  • A node is a leaf if and only if it is the end of a stored word.
  • Searching for an exact word is performed by appending $ to the query — any proper prefix will not have a $ edge.
  • In code, use the null character '\0' rather than a literal $, since $ might legitimately appear in strings.

Example Trie

The trie below stores: baby, bad, bank, banks, box, dog, dogs.

Key Insight — Reading a Trie
Follow the edges from the root, reading one character per edge. When you reach a node that has a $ child (or an is_terminal flag set), you have spelled out a complete stored word. You can also stop partway through to retrieve all words sharing that prefix (prefix matching).

§11.1 Operations on a Prefix Trie

Insert

Walk down the trie following the characters of the input string one by one. If the next child does not exist, create it. After processing all characters, mark the current node as terminal (or follow a $ edge).

Algorithm 62 — Prefix Trie: Insert Time: O(|s|) 
function INSERT(S[1..n]):
    node = root
    for each character c in S[1..n]:
        if node has an edge for character c:
            node = node.get_child(c)
        else:
            node = node.create_child(c)
    // At this point node represents the word S.
    // Mark terminal (create a '$' child or set node.is_terminal = True)

Lookup (Exact Search)

Walk the trie following each character of the query string (including a final $ if using terminator characters). If at any step the required child does not exist, the string is not stored. If we successfully consume all characters, the string is found.

Algorithm 63 — Prefix Trie: Lookup Time: O(|s|) 
function LOOKUP(S[1..n]):
    // Returns True if the trie contains a word having S as a prefix.
    // For exact match, append '$' to S before calling.
    node = root
    for each character c in S[1..n]:
        if node has an edge for character c:
            node = node.get_child(c)
        else:
            return False
    return True

Insight — Prefix vs Exact Match
LOOKUP("ban") returns True if any stored word starts with "ban" (e.g. "bank", "banks"). To check whether "ban" is itself stored, use LOOKUP("ban$") — this returns True only if the terminator edge exists at the node reached after "ban".

Prefix Matching (Autocomplete)

Walk to the node corresponding to the prefix (same as LOOKUP), then traverse the entire subtree rooted there and collect every path that ends with $. This returns all stored words that begin with the given prefix.

Complexity
O(|prefix| + U) where U is the total number of characters in all returned strings (output-sensitive).

String Sorting via Trie

Insert all strings into the trie (appending $ to each), then perform a depth-first traversal visiting children in alphabetical order. Each time a node with a terminal marker is reached, output the current accumulated string. This is equivalent to a Most Significant Digit (MSD) radix sort.

Algorithm 64 — Prefix Trie: String Sorting Time: O(|Σ| T) array-based 
function SORT_STRINGS(strings[1..n]):
    for each string s in strings[1..n]:
        INSERT(s + '$')
    TRAVERSE(root, "")

function TRAVERSE(node, cur_string):
    if cur_string ends with '$':
        print(cur_string)        // omit the '$' if desired
    else:
        for each child character c of node in alphabetical order:
            cur_string.append(c)
            TRAVERSE(node.get_child(c), cur_string)
            cur_string.pop_back()  // backtrack

Comparison with general-purpose sorting: sorting n strings of total length T using merge sort costs O(T log n) because each string comparison is O(T/n). The trie-based approach costs O(|Σ| T) for array-based nodes, or O(T log |Σ|) with BST-based child storage — better when |Σ| is constant or small.

§11.1 Implementation Strategies for Child Pointers

The central design decision in a trie implementation is how each node stores references to its children. Let n be the length of a query, T be the total length of all stored strings, and |Σ| be the alphabet size.

Strategy Space per node Total space Lookup time Notes
Array of size |Σ| O(|Σ|) O(|Σ| T) O(n) — O(1) per character Fastest; wastes space when nodes are sparse. Supports alphabetically nearest-key queries.
Balanced BST of children O(degree) O(T) O(n log |Σ|) — O(log |Σ|) per character Minimal space; supports nearest-key queries; slower than array.
Hash Table of children O(degree) O(T) O(n) expected — O(1) expected per character Optimal speed & space; but no deterministic worst-case, no nearest-key support.
Insight — Choosing an Implementation
For constant-sized alphabets (DNA: |Σ|=4, English: |Σ|=26) the array-based approach is typically preferred because the constant factor is small and O(1) child lookup is both fast and deterministic. For large or variable alphabets (e.g. Unicode), a hash table or BST is more space-efficient.

Properties of Any Trie

  • Maximum depth = length of the longest stored string.
  • Insert, Delete, Lookup time = O(length of string), regardless of how many strings are stored.
  • Deeper nodes tend to have fewer children — so the array-based approach wastes the most space near leaves.

§11.1 Compact (Patricia / Radix) Trie

A standard trie may contain long non-branching paths — chains where every internal node has exactly one child. These waste both time and space. The solution is to collapse such chains into a single edge whose label is the concatenated substring.

Definition — Compact / Compressed Trie
A compact trie (also called a Patricia trie or radix trie) is obtained from a standard trie by repeatedly merging every node that has exactly one child with its parent, combining their edge labels into a single string label on the merged edge. Every internal node in the resulting tree has at least two children.

Example

Consider the words alloy, aloe, allot, all in a standard trie. The path a → l → l is a three-step non-branching chain. In the compact trie it becomes a single edge labelled "all". The full compact trie for {be, ant, alloy, ate, are, aloe, an, allot, all} collapses many such chains. 

Standard fragment:           Compact equivalent:
root                         root
 └─ a                         ├─ "be" ──▶ [leaf: be]
     └─ l                     └─ "a"
         └─ l                      ├─ "n" ──▶ [an$]
             └─ o                  │    └─ "t" ──▶ [ant$]
                 └─ y (leaf)       ├─ "te" ──▶ [ate$]
                                   ├─ "re" ──▶ [are$]
                                   └─ "l"
                                        ├─ "oe" ──▶ [aloe$]
                                        └─ "l"
                                             ├─ $ ──▶ [all$]
                                             ├─ "ot" ──▶ [allot$]
                                             └─ "oy" ──▶ [alloy$]
Space Improvement
A compact trie over n strings has at most n leaves and at most n−1 internal nodes, so at most 2n−1 nodes total — regardless of string lengths. Edge labels are stored as (start, length) index pairs into the original strings, keeping total space O(T).

Theorem — Trie Sorting vs Merge Sort
Sorting n strings of total length T using merge sort costs O(T log n) because each comparison is O(T/n). The trie-based approach costs O(T) for constant alphabets. Trie sorting therefore wins whenever |Σ| is constant — it is essentially MSD radix sort.

§11.1 Trie vs Hash Table vs BST

Feature Prefix Trie Hash Table BST (string keys)
Exact lookup O(M) — deterministic O(M) expected O(M log N)
Prefix matching O(M + U) Not supported efficiently O(M log N + U)
Sorted order iteration Yes — O(T) No Yes — O(T)
Nearest-key query Yes (array/BST nodes) No Yes
Space O(|Σ| T) worst case O(T) O(T)
Worst-case guarantee Yes No (hash collisions) Yes (balanced BST)

Practical Applications of Tries

  • Autocomplete / Autocompletion: Given a typed prefix, list the top-k most frequent completions — trie prefix match then rank by frequency stored at nodes.
  • Spell checking: Exact lookup for words; nearest-key traversal for suggestions.
  • IP routing (longest prefix match): Routers store IP prefixes in tries; incoming packet addresses are matched to the longest matching prefix in O(32) = O(1) steps.
  • Lexicographic string sorting: In-order DFS of trie yields sorted output.
  • Text search / dictionary lookups: As a replacement for hash tables where prefix queries are needed.

§11.2 Suffix Trees — Motivation

Tries are excellent for looking up complete words (or prefixes of words), but what about searching for an arbitrary substring of a large text? The key observation is:

Key Insight — Substrings as Prefixes of Suffixes
Every substring of a string S[1..n] is a prefix of some suffix of S. Therefore, if we build a trie of all suffixes of S, any pattern P can be found by a simple prefix lookup — we just follow P down from the root. If the traversal succeeds, P occurs in S.

Problem Statement — Pattern Matching

Problem
Given a text string T[1..n] and a pattern P[1..m], find all occurrences of P as a substring of T.

Many algorithms (Knuth-Morris-Pratt, Boyer-Moore) solve this in O(n + m) per query. However, if we wish to keep the same text and answer many pattern queries, paying O(n) per query is wasteful — especially when n = 1,000,000 and m = 20. A suffix tree pre-processes T in O(n) (with Ukkonen's algorithm) and then answers each query in O(m).

From Suffix Trie to Suffix Tree

A suffix trie is a standard (uncompressed) prefix trie built from all suffixes of S. It supports O(m) pattern matching queries but requires O(n²) space — a string of length n has n suffixes whose total length is 1 + 2 + ... + n = O(n²). This is impractical.

Compressing the suffix trie into a compact trie — called a suffix tree — brings space down to O(n) while preserving O(m) query time.

§11.2 Suffix Tree — Definition & Properties

Definition — Suffix Tree
A suffix tree for string S is a compact (compressed) trie of all suffixes of S (typically with a unique terminator character $ appended to S so that no suffix is a prefix of another). Each leaf corresponds to exactly one suffix of S, and the path from the root to that leaf spells out that suffix. Each edge label is a substring of S (stored as an index pair, not explicitly).

Structural Properties

  • S has n suffixes (where n = |S|, after appending $ it has n+1 suffixes), so the suffix tree has exactly n+1 leaves.
  • Every internal node has at least 2 children (guaranteed by the compression; any node with one child would have been merged with its parent).
  • There are at most n internal nodes (since the tree has n+1 leaves and is full — every internal node has ≥2 children).
  • Total number of nodes: O(n).
  • The total length of all edge labels is O(n) — this is the key advantage over the suffix trie.
  • Each edge label is stored as a pair (start, length) or (start, end) pointing into the original string S, so the entire tree uses only O(n) space.

Reading a Suffix Tree
The label at each leaf indicates the starting position of that suffix in the original string. To find whether pattern P occurs in S: follow P from the root, one character at a time along edge labels. If you successfully consume all of P, you have found it; the leaves of the current subtree give you all starting positions of P in S.

Space Representation

Rather than storing edge labels as actual substrings (which would require O(n²) space total), each edge label is stored as an integer pair [x, y] meaning "the substring of S from index x to index y". For example, in banana$, the edge label "na" is stored as [3, 4]. This reduces total space to O(n).

Space Complexity — Suffix Tree
  • Exactly n+1 leaves.
  • At most n internal nodes.
  • Each node stores two integers (start, end) for its incoming edge label.
  • Total: O(n) space.

§11.2.1 Building a Suffix Tree

Naive Construction — O(n²)

The simplest approach is:

  1. Build the full (uncompressed) suffix trie by inserting all n suffixes of S into a standard trie. The i-th suffix has length n−i+1, so total insertion cost is 1 + 2 + ... + n = O(n²).
  2. Compress the trie by collapsing all non-branching chains into single edges. This traversal also takes O(n²).

Total naive construction time: O(n²). This is simple to implement but impractical for large strings.

Ukkonen's Algorithm — O(n) (Not examinable in Semester 1, 2026)

Ukkonen (1995) gave an elegant online, linear-time algorithm for suffix tree construction. It processes S one character at a time, maintaining the suffix tree for the current prefix of S. Key ideas:

  • Each new character extends all existing leaf edges by one character — this is done implicitly in O(1) by using an end pointer shared among all leaves.
  • Whenever a new character would cause a suffix to diverge from an existing path, a new internal node and leaf are created by splitting an edge.
  • Suffix links (pointers from an internal node to the internal node representing the same string minus its first character) allow efficient navigation between related nodes.
Theorem — Ukkonen's Algorithm
Ukkonen's algorithm constructs a suffix tree for a string of length n in O(n) time and space. It is also online: characters can be appended to S incrementally without rebuilding from scratch.

Practical Representation

In any implementation, edge labels are stored as (start, end) index pairs into the original string rather than as copied substrings. Leaf edges use a global "current end" variable that is incremented as the string grows, achieving the O(1) implicit extension for all leaves simultaneously.

MethodTimeSpace

§11.2.2 Applications of Suffix Trees

1. Pattern Matching

Problem
Does pattern P[1..m] occur as a substring of text S[1..n]?

Algorithm: Start at the root of the suffix tree for S. For each character of P, follow the matching edge (checking characters along each edge label). If at any point no matching edge exists, P does not occur in S. If all of P is consumed, P occurs in S — the current subtree contains the positions of all occurrences.

Pattern Matching via Suffix Tree Query: O(|P|)  |  Pre-processing: O(|S|) 
function PATTERN_MATCH(root, S, P[1..m]):
    node = root
    p_idx = 1
    while p_idx <= m:
        // Find the edge from node whose label starts with P[p_idx]
        edge = node.get_edge_starting_with(P[p_idx])
        if edge is None:
            return NOT_FOUND
        // Walk along this edge, matching P against the edge label
        for each character c in edge.label:
            if p_idx > m:
                break           // all of P consumed — found!
            if P[p_idx] != c:
                return NOT_FOUND
            p_idx += 1
        node = edge.target
    return FOUND   // subtree leaves give all occurrence positions
Complexity
  • Pre-processing (build suffix tree): O(n) with Ukkonen; O(n²) naively.
  • Each query: O(m) — optimal, since you must read all of P.
Compare: naive O(nm) per query; KMP O(n+m) per query but O(n) work even for tiny patterns.

2. Counting Occurrences

Problem
How many times does pattern P[1..m] appear in text S[1..n]?

After locating the node where the traversal for P terminates (same as pattern matching above), the number of occurrences equals the number of leaves in the subtree rooted at that node — since each leaf corresponds to exactly one suffix, and each suffix that starts with P records one occurrence of P.

To answer counting queries efficiently, pre-compute the number of leaves in every subtree during a single O(n) DFS over the suffix tree. After this O(n) preprocessing, each count query runs in O(m).

Summary
Pre-process: O(n) DFS to store leaf counts at every node. Query: O(m) to walk P from the root; O(1) to read the leaf count.

In the uncompressed suffix trie, the same counting method applies: count the number of leaf nodes (nodes with a $ child) in the subtree. If leaf counts are maintained during insertion, each query is O(m) even without the separate preprocessing DFS.

3. Longest Repeated Substring

Problem
Given string S[1..n], find the longest substring that appears at least twice in S.

Key insight: In a suffix tree, every internal node corresponds to a substring that is a prefix shared by at least two suffixes — meaning it occurs at least twice in S. Leaf nodes correspond to substrings appearing exactly once. Therefore, the longest repeated substring is the string spelled out by the path from the root to the deepest internal node, where depth is measured by string depth (total number of characters on the path from root to that node, summing edge label lengths).

Longest Repeated Substring Time: O(n) after O(n) tree construction 
function LONGEST_REPEATED_SUBSTRING(suffix_tree):
    best_node = None
    best_depth = 0
    // DFS, tracking current string depth (sum of edge label lengths)
    for each internal node v in suffix_tree (DFS):
        depth = string_depth(v)   // total chars from root to v
        if depth > best_depth:
            best_depth = depth
            best_node = v
    return path_label(best_node)   // the repeated substring
Example — "banana$"
In the suffix tree for banana$, the deepest internal node has string depth 3, corresponding to the substring "ana". Indeed, "ana" appears at positions 1 and 3 in banana.

4. Longest Common Substring of Two Strings

Problem
Given two strings S[1..n] and T[1..k], find the longest substring common to both.

Algorithm: Build a generalised suffix tree — a suffix tree containing the suffixes of both strings. To avoid ambiguity, append unique terminators: use S# and T$ (where # and $ are distinct characters not in the alphabet). Each leaf is tagged as belonging to S or T (or both, if the same suffix happens to exist in both strings).

The longest common substring corresponds to the deepest internal node that has at least one leaf from S and at least one leaf from T in its subtree. Finding this node requires:

  1. Build the generalised suffix tree of S#T$: O(n + k).
  2. Annotate each node with whether its subtree contains leaves from S, leaves from T, or both: O(n + k) DFS.
  3. Find the deepest annotated node that has both: O(n + k) DFS.
Complexity
Total: O(n + k) after O(n + k) construction. Compare: naive O(nk·min(n,k)) dynamic programming.
Extension — Multiple Strings
The same idea generalises: given strings S₁, S₂, ..., Sₚ, find the longest substring occurring in at least k of them. Build a generalised suffix tree of all strings, annotate each node with the set of source strings in its subtree, and find the deepest node whose annotation set has size ≥ k.

5. Lexicographic Sorting of Suffixes

A DFS of the suffix tree, always choosing children in alphabetical order of their edge labels, visits the leaves in lexicographic order of the suffixes. The leaf indices encountered form the suffix array of S. This is an O(n) extraction of the suffix array from the suffix tree (after O(n) construction).

Applications Summary

Application Pre-processing Query time Key idea
Pattern matching (exists?) O(n) build O(m) Walk P from root; fall off = not found
Count occurrences of P O(n) build + O(n) DFS O(m) Leaf count in subtree where P ends

§ Key Takeaways

Core Messages
  • Tries give O(M) insert and lookup for strings of length M — independent of how many strings are stored. This beats BSTs (O(M log N)) and is competitive with hash tables while supporting richer queries.
  • Compact (Patricia) tries reduce the node count to O(n) for n strings, making the structure space-efficient.
  • Suffix trees are compact tries over all suffixes of a text — they enable O(m) pattern matching after O(n) preprocessing (with Ukkonen's algorithm), outperforming per-query algorithms like KMP when many queries are issued against the same text.
  • Storing edge labels as (start, end) index pairs is essential to keep suffix tree space at O(n) rather than O(n²).
  • Both tries and suffix trees support linear-time construction, though the suffix tree construction algorithm (Ukkonen) is non-trivial.
Common Pitfalls
  • Confusing a suffix trie (uncompressed, O(n²) space) with a suffix tree (compressed, O(n) space). The suffix tree is the one used in practice.
  • Forgetting the terminal character $: without it, some suffix could be a prefix of another, and leaf nodes would not correctly correspond to full suffixes.
  • Confusing string depth (total characters on path from root to node) with node depth (number of edges): the deepest internal node by string depth gives the longest repeated substring, not the deepest by edge count.
  • Storing edge labels as actual substrings rather than index pairs inflates space to O(n²).
